# 第二章：数据库设计 — database.py 与 models.py

数据库是论坛的地基。这一章我们先看"怎么连数据库"（database.py），再看"数据怎么组织"（models.py 里的 8 张表）。

## 2.1 数据库连接（database.py）

```python
import os
from collections.abc import Generator
from urllib.parse import unquote, urlparse

from sqlalchemy import create_engine, text
from sqlalchemy.engine import URL as EngineURL
from sqlalchemy.orm import Session, sessionmaker, DeclarativeBase

DATABASE_URL = os.environ.get("DATABASE_URL", "postgresql://blog:blog@localhost:5432/blog")

_parsed = urlparse(DATABASE_URL)

engine_url = EngineURL.create(
    "postgresql+psycopg2",
    username=unquote(_parsed.username) if _parsed.username else None,
    password=unquote(_parsed.password) if _parsed.password else None,
    host=_parsed.hostname,
    port=_parsed.port,
    database=_parsed.path.lstrip("/") or "blog",
)

engine = create_engine(engine_url, connect_args={"client_encoding": "utf8"})
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)


class Base(DeclarativeBase):
    pass


def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

### 为什么要把 URL 拆开重拼？

这一眼看上去有点啰嗦：`create_engine(DATABASE_URL)` 不就能用吗？**不能**，至少在 Windows 上不行。

`DATABASE_URL` 是一个标准连接串，格式是 `postgresql://用户名:密码@主机:端口/库名`。如果密码里出现了 `@`、`:`、`/` 这类字符，直接交给 psycopg2 解析会出错。更麻烦的是 Windows 下 psycopg2 处理带非 ASCII 字符的连接串时经常抛出编码异常。

所以这里用 `urlparse` 先把连接串拆成五个部分，再用 `EngineURL.create()` 重新组装。拆开的过程中：
- 用 `unquote()` 把 URL 里 `%40` 之类的百分号编码还原成原始字符
- 明确指定驱动是 `postgresql+psycopg2`
- 显式传入 `connect_args={"client_encoding": "utf8"}`，强制客户端编码为 UTF-8

一句话总结：**这是为了在 Windows + 中文/特殊字符密码下也能稳定连上数据库**，把"URL 解析"这件事交给 Python 而不是交给驱动。

### 关键概念

- **create_engine** — 创建数据库连接池，管理复用连接
- **SessionLocal** — 会话工厂，每次请求创建一个 Session（工作单元）
- **DeclarativeBase** — 所有模型类的基类，ORM 通过它发现表定义
- **get_db()** — 生成器函数，FastAPI 用它做依赖注入，请求开始获取 Session、请求结束自动关闭

> **没有 SQLite 回退**。很多教程会给 SQLite 留一条后路方便本地跑，这个项目刻意不做。PostgreSQL 是唯一路径，因为两边在布尔类型、大小写敏感、`ON DELETE CASCADE`、索引行为上差异太多，一旦本地用 SQLite 调试、线上用 PG，"本地好好的、线上炸了"会非常难查。

### ensure_schema() — 启动时的轻量建表

```python
def ensure_schema():
    """Create tables and apply lightweight migrations."""
    # PostgreSQL 15+ 默认撤销了 public schema 的 CREATE 权限，需要显式授权。
    # 云数据库（RDS、Supabase 等）可能不允许 GRANT，失败时只警告不崩溃。
    try:
        with engine.begin() as conn:
            conn.execute(text("GRANT CREATE ON SCHEMA public TO CURRENT_USER"))
    except Exception:
        import logging
        logging.getLogger("blog").warning(
            "无法在 public schema 上授权 CREATE（云数据库通常已预先配置好权限），跳过"
        )

    Base.metadata.create_all(bind=engine)

    with engine.begin() as conn:
        conn.execute(text(
            "ALTER TABLE comments ADD COLUMN IF NOT EXISTS parent_id INTEGER REFERENCES comments(id)"
        ))
        conn.execute(text(
            "ALTER TABLE topics ADD COLUMN IF NOT EXISTS is_pinned BOOLEAN DEFAULT FALSE"
        ))
        conn.execute(text(
            "ALTER TABLE topics ADD COLUMN IF NOT EXISTS is_featured BOOLEAN DEFAULT FALSE"
        ))
```

这个函数做三件事，缺一不可：

1. **尝试授权 `GRANT CREATE ON SCHEMA public TO CURRENT_USER`**。PostgreSQL 15 起默认收回了 `public` schema 的建表权限，新库不授权就会建表失败。但云数据库（RDS、Supabase 等）往往已经预先配好权限、且不允许普通用户 GRANT，所以用 `try/except` 包起来——失败只打一条 warning，不让服务启动崩溃
2. **`Base.metadata.create_all(bind=engine)`** — SQLAlchemy 扫描所有继承 `Base` 的模型，对不存在的表执行 `CREATE TABLE`（已存在的表会跳过）
3. **三条 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`** — 给老库补上后加的列

注意第 3 步只处理了 `comments.parent_id`、`topics.is_pinned`、`topics.is_featured` 三个"后加的列"。这套机制能加列，但**不能删列、不能改名、不能改类型**——第八章会专门讨论它的能力边界，以及为什么项目最终没有引入 Alembic。

## 2.2 八张表总览

| 表名 | 用途 | 核心字段 |
|------|------|---------|
| **users** | 用户账号信息 | username, password_hash, avatar, is_admin, topic_count |
| **topics** | 帖子/话题 | title, content, author_id, view_count, is_pinned, is_featured |
| **comments** | 评论与回复 | content, topic_id, user_id, parent_id |
| **likes** | 用户点赞关系 | user_id + topic_id（联合主键） |
| **notifications** | 站内通知 | user_id, type, topic_id, comment_id, is_read |
| **messages** | 用户私信 | sender_id, receiver_id, content, is_read |
| **tags** | 标签 | name, slug |
| **topic_tags** | 帖子↔标签关联 | topic_id + tag_id（联合主键） |

## 2.3 User 模型

```python
class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True, index=True)
    username = Column(String, unique=True, nullable=False, index=True)
    password_hash = Column(String, nullable=False)
    avatar = Column(String, default="")
    bio = Column(String, default="")
    github_url = Column(String, default="")
    is_admin = Column(Boolean, default=False)
    topic_count = Column(Integer, default=0)
    comment_count = Column(Integer, default=0)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

    topics = relationship("Topic", back_populates="author")
    comments = relationship("Comment", back_populates="author")
```

### 字段设计要点

- **主键 id**：自增整数，每行记录的唯一标识
- **unique=True + index=True**：保证用户名唯一，同时加索引加速"按用户名查找"（登录时高频操作）
- **password_hash**：存 bcrypt 加密后的密码，**绝不存明文**
- **is_admin**：管理员开关，决定能否删除他人内容、置顶/加精帖子
- **topic_count/comment_count**：冗余统计字段，避免每次都要 COUNT 查询（以空间换时间）
- **default=lambda: datetime.now(timezone.utc)**：用 lambda 确保创建记录时才获取时间，而不是模块加载时

## 2.4 Topic 模型 — 帖子

```python
class Topic(Base):
    __tablename__ = "topics"

    id = Column(Integer, primary_key=True, index=True)
    title = Column(String, nullable=False)
    content = Column(Text, default="")
    author_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    view_count = Column(Integer, default=0)
    is_pinned = Column(Boolean, default=False)
    is_featured = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))
    updated_at = Column(
        DateTime,
        default=lambda: datetime.now(timezone.utc),
        onupdate=lambda: datetime.now(timezone.utc),
    )

    author = relationship("User", back_populates="topics")
    comments = relationship("Comment", back_populates="topic", cascade="all, delete-orphan")
    likes = relationship("User", secondary="likes")
    tags = relationship("Tag", secondary="topic_tags")
```

### 关键关系

- **author_id** — 外键指向 users.id，表示"谁发的帖"
- **updated_at** — `default` 是创建时时间，`onupdate` 是每次更新自动刷新
- **is_pinned / is_featured** — 两个布尔标记，分别对应"置顶"和"加精"。置顶的帖子在列表排最前（排序逻辑在第四章 `get_topics` 里），加精则是给内容打一个推荐标记
- **cascade="all, delete-orphan"** — 删帖时自动删除所有关联评论
- **secondary="likes"** — 多对多关系桥接 likes 中间表
- **secondary="topic_tags"** — 多对多关系桥接标签表。一个帖子可以有多个标签，一个标签也可以属于多个帖子

## 2.5 Comment 模型 — 楼中楼实现

```python
class Comment(Base):
    __tablename__ = "comments"

    id = Column(Integer, primary_key=True, index=True)
    content = Column(Text, nullable=False)
    topic_id = Column(Integer, ForeignKey("topics.id"), nullable=False)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    parent_id = Column(Integer, ForeignKey("comments.id"), nullable=True)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

    topic = relationship("Topic", back_populates="comments")
    author = relationship("User", back_populates="comments")
    parent = relationship("Comment", remote_side="Comment.id", back_populates="replies")
    replies = relationship("Comment", back_populates="parent", cascade="all, delete-orphan")

    __table_args__ = (
        Index("ix_comments_topic_id", "topic_id"),
        Index("ix_comments_parent_id", "parent_id"),
    )

    @property
    def username(self):
        return self.author.username if self.author else ""
```

### 自引用实现原理

```
评论1（parent_id=NULL）           ← 顶层评论
  ├── 回复1.1（parent_id=评论1）   ← 对评论1的回复
  │   └── 回复1.1.1（parent_id=回复1.1）  ← 嵌套回复
  └── 回复1.2（parent_id=评论1）
评论2（parent_id=NULL）           ← 另一条顶层评论
```

- `parent_id IS NULL` → 顶层评论，直接回复帖子
- `parent_id = 5` → 对 id=5 的评论的回复
- `remote_side="Comment.id"` — 告诉 SQLAlchemy 自引用中"父"的一方是 id

### 为什么单独声明索引？

`topic_id` 和 `parent_id` 的 `Column` 上其实没有写 `index=True`，索引是通过 `__table_args__` 单独声明的：

```python
__table_args__ = (
    Index("ix_comments_topic_id", "topic_id"),
    Index("ix_comments_parent_id", "parent_id"),
)
```

作用一样，但更显式、可命名。这两个索引正好对应评论系统里最频繁的两类查询："某帖子的所有评论"和"某评论的所有回复"——没有索引，帖子一火评论一多就会全表扫描。

### `@property username` 的小技巧

数据库里评论只存了 `user_id`，没有用户名。但 API 返回给前端时需要 `username`。于是模型上加了一个只读属性，把 `self.author.username` 转发出去：

```python
@property
def username(self):
    return self.author.username if self.author else ""
```

这样 `comment.username` 用起来就像评论自己的字段一样。第三章讲 Pydantic 的 `field_validator` 时你会看到它如何与这个属性配合。

## 2.6 Notification 模型 — 站内通知

```python
class Notification(Base):
    __tablename__ = "notifications"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False)
    type = Column(String, nullable=False, default="reply")
    topic_id = Column(Integer, ForeignKey("topics.id", ondelete="CASCADE"), nullable=True)
    comment_id = Column(Integer, ForeignKey("comments.id", ondelete="CASCADE"), nullable=True)
    is_read = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

    __table_args__ = (
        Index("ix_notifications_user_read", "user_id", "is_read"),
    )
```

- **type** — 通知类型（"reply"），预留扩展空间
- **topic_id + comment_id** — 记录上下文，点击通知时跳转到对应帖子/评论
- **ondelete="CASCADE"（数据库级联）** — 三个外键都带这个。注意它和 ORM 层的 `cascade` 不是一回事：`ondelete` 写在数据库的 `FOREIGN KEY ... ON DELETE CASCADE` 上，帖子被删时数据库直接连带删掉相关通知，不需要 ORM 参与
- **复合索引 `(user_id, is_read)`** — 未读数查询是"某个用户 + 未读"这两个条件，复合索引能让它走索引而不是扫全表

## 2.7 Message 模型 — 私信

```python
class Message(Base):
    __tablename__ = "messages"

    id = Column(Integer, primary_key=True, index=True)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    receiver_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    is_read = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

    sender = relationship("User", foreign_keys=[sender_id])
    receiver = relationship("User", foreign_keys=[receiver_id])

    __table_args__ = (
        Index("ix_messages_sender_receiver", "sender_id", "receiver_id"),
        Index("ix_messages_receiver_read", "receiver_id", "is_read"),
    )
```

### 两个外键指向同一张表：必须指定 foreign_keys

`sender_id` 和 `receiver_id` 都指向 `users.id`。如果只写 `relationship("User")` 两次，SQLAlchemy 会懵：到底哪个外键对应哪个关系？所以必须用 `foreign_keys=[...]` 明确指出：

```python
sender = relationship("User", foreign_keys=[sender_id])
receiver = relationship("User", foreign_keys=[receiver_id])
```

这正是"自引用/多重外键"场景下的标准解法。

### 两个索引的分工

- `(sender_id, receiver_id)` — 查"我和某人之间的聊天记录"时用
- `(receiver_id, is_read)` — 查"我有多少条未读"时用

索引不是越多越好，但这两个正好覆盖私信模块最高频的两种查询。

## 2.8 标签：Tag 模型 + topic_tags 中间表

```python
class Tag(Base):
    __tablename__ = "tags"

    id = Column(Integer, primary_key=True, index=True)
    name = Column(String, unique=True, nullable=False, index=True)
    slug = Column(String, unique=True, nullable=False, index=True)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))


topic_tags = Table(
    "topic_tags",
    Base.metadata,
    Column("topic_id", Integer, ForeignKey("topics.id"), primary_key=True),
    Column("tag_id", Integer, ForeignKey("tags.id"), primary_key=True),
)
```

- **name 与 slug 都唯一** — `name` 是给人看的（如 `Python`），`slug` 是给 URL/查重用的规范化形式（如 `python`）。为什么要两个？因为标签查重靠 slug，而显示用原始 name，这样"Python"和"python"会被认为是同一个标签
- **topic_tags 只定义 Table，不定义 ORM 类** — 关联表本身没有额外字段时，用 Table 对象最省事

## 2.9 likes 中间表

```python
likes = Table(
    "likes",
    Base.metadata,
    Column("user_id", Integer, ForeignKey("users.id"), primary_key=True),
    Column("topic_id", Integer, ForeignKey("topics.id"), primary_key=True),
)
```

- 不定义 ORM 类，只用 Table 对象
- **联合主键**保证：同一个用户不能给同一个帖子点两次赞——这是数据库层面的约束，也是第四章"点赞幂等"实现的基础

## 表关系总结

```
users ──┬── topics（一对多：一个用户有多篇帖子）
        ├── comments（一对多：一个用户有多条评论）
        ├── likes（多对多：用户↔帖子）
        └── messages（一对多 ×2：作为发送者/接收者）

topics ──┬── comments（一对多：一个帖子有多条评论）
         ├── likes（多对多）
         └── tags（多对多：经 topic_tags）

comments ── self（自引用：评论可以回复评论）

users ── notifications（一对多：接收者的通知箱）
```

## 本章要点

- ORM 的核心：用 Python 类描述数据库表，用 relationship 描述表间关系
- 四种关系模式：一对多（ForeignKey）、多对多（secondary）、自引用（remote_side）、多重外键（foreign_keys）
- `ensure_schema` / 连接串拆分 / 无 SQLite 回退——这个项目的数据库层为"只跑 PostgreSQL"做了取舍
- 索引按查询模式来加：评论的 topic_id/parent_id、通知的 (user_id, is_read)、私信的两种组合
- 冗余字段：topic_count/comment_count 以空间换时间
- 默认值：用 lambda 延迟求值，避免模块加载时固定时间
