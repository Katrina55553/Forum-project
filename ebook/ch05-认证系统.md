# 第五章：认证系统 — auth.py

认证系统是后端的**安全大门**，处理三个核心问题：

1. **密码加密** — 注册时存 bcrypt 哈希，不存明文
2. **JWT 签发** — 登录成功后颁发令牌（token），后续请求带着它证明身份
3. **身份解析** — 从 HTTP Header 取出 token，识别出当前用户

整个 `auth.py` 只有 90 行，但它是所有需要登录的接口的地基。

```python
import os
from datetime import datetime, timedelta, timezone

import bcrypt
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from jose import JWTError, jwt
from sqlalchemy.orm import Session

from database import get_db
from models import User

SECRET_KEY = os.environ.get("SECRET_KEY") or "dev-only-change-me"
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_HOURS = 24

security = HTTPBearer()
```

> ⚠️ `SECRET_KEY` 必须通过环境变量设置，绝不能硬编码！默认值 `dev-only-change-me` 只是开发占位符——第 9 章你会看到 `deploy.sh` 在没有 `.env` 时用 `openssl rand -hex 32` 生成一个真正的随机密钥。

这里用的是 `os.environ.get("SECRET_KEY") or "..."` 而不是 `os.environ.get("SECRET_KEY", "...")`。两者在"变量不存在"时行为一样，但**如果环境变量存在却为空字符串**，前者会回退到默认值、后者会拿到空串——用 `or` 更稳妥。

## 密码加密

```python
def hash_password(password: str) -> str:
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt()).decode()

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return bcrypt.checkpw(plain_password.encode(), hashed_password.encode())
```

| 函数 | 做的事 | 场景 |
|------|--------|------|
| `hash_password` | 密码 → 加盐 → bcrypt 加密 → 存库 | 注册、改密码 |
| `verify_password` | 明文密码 + 数据库 hash → 比对 | 登录时 |

**为什么用 bcrypt？** bcrypt 故意设计得很"慢"（消耗计算资源），而且内置盐值（salt），即使用户 A 和 B 密码相同，加密结果也不同。攻击者拿到数据库也无法用彩虹表批量反查——每试一个密码都要付出一次 bcrypt 的代价。

### 一段版本历史：为什么会直接用 bcrypt 库

项目早期用的是 `passlib`——一个统一封装了多种哈希算法的库，常见写法是 `passlib.context.CryptContext(schemes=["bcrypt"])`。后来 passlib 与新版 `bcrypt` 库之间出现了版本不兼容（passlib 去读取 bcrypt 的内部属性，而新版 bcrypt 移除了它），调用时会抛异常。

于是项目做了一个干脆的决定：**去掉 passlib，直接调用 `bcrypt` 库本身**。依赖清单里只剩 `bcrypt` 一行，`hash_password` / `verify_password` 直接调 `bcrypt.hashpw` / `bcrypt.checkpw`。代码没有变复杂，反而更直白——遇到"中间层库跟不上底层库更新"的情况，删掉中间层往往比锁死版本更划算。

## JWT 令牌

```python
def create_access_token(data: dict) -> str:
    to_encode = data.copy()
    expire = datetime.now(timezone.utc) + timedelta(hours=ACCESS_TOKEN_EXPIRE_HOURS)
    to_encode.update({"exp": expire})
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

def decode_token(token: str) -> dict | None:
    try:
        return jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except JWTError:
        return None
```

JWT 格式：`header.payload.signature`

解码后内容：

```json
{"sub": "1", "exp": 1717200000}
```

- `sub`（subject）— JWT 标准字段，存放用户 ID（`create_access_token` 收到的是 `{"sub": str(user.id)}`，转成字符串是因为 JWT 规范要求 sub 是字符串）
- `exp`（expiration）— 过期时间戳，24 小时后失效
- `decode_token` 把 "签名不对 / 过期 / 格式错" 都统一成返回 `None`，调用方只需要判 `None`，不必逐个处理各类异常

**无状态认证**：服务器不存 token，全靠签名验证真伪，水平扩展不需要共享 session 存储。token 一旦签发就无法单独吊销——这也是为什么有效期只给了 24 小时。

## FastAPI 依赖注入 — 身份解析

三个依赖函数对应三种访问控制强度，是整个认证策略的骨架。

### 必须登录

```python
def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security),
    db: Session = Depends(get_db),
) -> User:
    payload = decode_token(credentials.credentials)
    if payload is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token")
    sub = payload.get("sub")
    if not sub:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token")
    try:
        user_id = int(sub)
    except (TypeError, ValueError):
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid token")
    user = db.query(User).filter_by(id=user_id).first()
    if user is None:
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="User not found")
    return user
```

它比"教科书版本"多了两道防御：

- **`sub` 是否存在** — 签名的 payload 不一定有 `sub`，直接 `int(None)` 会抛 `TypeError` 变成 500。这里先判断再转换
- **`int(sub)` 包在 `try/except` 里** — 防止有人构造出 `sub` 不是数字的 token（虽然签名验证会挡住绝大多数，但"能解析出 payload 但不合法"的情况仍需兜底）。三种失败情况都返回统一的 401

`HTTPBearer()` 在这条路径上是"必须带 token"：没带 Authorization 头时，FastAPI 自动返回 403；带了但 token 无效时才轮到上面这段逻辑返回 401。仔细体会这两者的区别，前端拦截器里判断的正是 401。

在路由中使用：

```python
@app.get("/api/auth/me", response_model=UserResponse)
def me(current_user: User = Depends(get_current_user)):
    return current_user   # 只允许登录用户访问
```

### 可选登录

```python
optional_security = HTTPBearer(auto_error=False)

def get_optional_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(optional_security),
    db: Session = Depends(get_db),
) -> User | None:
    """Like get_current_user but returns None instead of 401 for unauthenticated requests."""
    if credentials is None:
        return None
    payload = decode_token(credentials.credentials)
    if payload is None:
        return None
    sub = payload.get("sub")
    if not sub:
        return None
    try:
        user_id = int(sub)
    except (TypeError, ValueError):
        return None
    return db.query(User).filter_by(id=user_id).first()
```

关键差别有两个：

- **`HTTPBearer(auto_error=False)`** — 没带 token 时不报错，而是让 `credentials` 为 `None`
- **所有失败路径都返回 `None`** — token 无效、用户不存在，对"可选登录"接口来说都等同于游客，一律当成未登录处理

应用场景：帖子详情页。已登录能看到"取消点赞"，未登录看到"点赞"——同一个 API，用 `is_liked` 区分。详情路由用 `get_optional_user`，所以**游客也能看帖**，只是拿不到 `is_liked` 的个人化信息。

### 管理员检查

```python
def require_admin(
    current_user: User = Depends(get_current_user),
) -> User:
    if not current_user.is_admin:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Admin required")
    return current_user
```

`require_admin` 是**建立在 `get_current_user` 之上**的二段式检查：它自己不碰 token，直接依赖已经解析好的 `current_user`。这带来一个很优雅的效果——未登录访问需要管理员的接口会先得到 401（来自 `get_current_user`），登录了但不是管理员才得到 403。三种访问强度就这样层层叠加，代码却不重复。

它被用在置顶和加精两个接口上：

```python
@app.put("/api/topics/{topic_id}/pin")
def pin_topic_route(topic_id: int, current_user: User = Depends(require_admin), db: Session = Depends(get_db)):
    ...
```

## 三种访问控制一览

| 依赖 | 未登录 | 已登录 | 管理员 | 典型用途 |
|------|:------:|:------:|:------:|---------|
| `get_optional_user` | 放行（None） | 放行 | 放行 | 帖子详情、列表 |
| `get_current_user` | 401 | 放行 | 放行 | 发帖、评论、私信、个人资料 |
| `require_admin` | 401 | 403 | 放行 | 置顶、加精 |

## 认证流程总结

```
注册 → bcrypt 加密密码 → 存入数据库

登录 → 查数据库 → verify_password 比对
     → 通过？生成 JWT（含 user_id + 过期时间）
     → 返回 token 给客户端

后续请求 → Header: Authorization: Bearer xxx
         → get_current_user 解码 JWT → 查数据库 → 返回 User 对象
```

## 本章要点

- 密码只存 bcrypt 哈希，绝不留明文；直接调用 `bcrypt` 库，不再经 passlib
- JWT 是"无状态"的：服务端不存 session，靠签名自证；代价是无法单独吊销，只能缩短有效期
- 三个依赖对应三种访问强度：`get_optional_user`（可为游客）、`get_current_user`（401）、`require_admin`（403）
- `decode_token` 把各类 JWT 异常统一收敛成 `None`；`int(sub)` 必须包 try/except 防 500
- 权限检查层层复用：`require_admin` 依赖 `get_current_user`，不重复解析 token
