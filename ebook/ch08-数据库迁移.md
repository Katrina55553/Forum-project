# 第八章：数据库迁移

## 两种完全不同性质的"迁移"

聊迁移之前，先把一件容易混淆的事讲清楚：这个项目里存在两种东西，名字都像"迁移"，但性质完全不同。

| | `backend/migrations/001_blog_to_forum.sql` | `database.py` 的 `ensure_schema()` |
|---|---|---|
| 性质 | **历史一次性脚本** | **当前日常手段** |
| 何时执行 | 只在 blog→forum 改造时手工跑过一次 | 每次服务启动自动执行 |
| 能做什么 | 重命名表、删列、重建表（复杂的 DDL） | 只能建新表、**加**列 |
| 现在还要不要跑 | **不要**，跑了会破坏数据 | 一直是它 |

很多教程讲迁移时会直接上 Alembic，但这个项目没有引入 Alembic。它是一个个人项目，选择了"够用就好"的轻量方案。这一章就来诚实地说清楚这个方案是怎么工作的、以及它的局限。

## 001_blog_to_forum.sql — 一份历史档案

`backend/migrations/001_blog_to_forum.sql` 是整个项目唯一一个迁移脚本。它记录的是项目早期的一次大改造：**原本是一个博客系统，后来改造成了论坛**。

```sql
-- 001_blog_to_forum.sql
-- 将博客数据模型迁移为论坛数据模型
--
-- WARNING: 此迁移会清空 likes、post_tags、tags 表数据。
-- slug/summary/status 列也被删除。仅保留用户账号。

BEGIN;

-- 1. 重命名 posts → topics
ALTER TABLE posts RENAME TO topics;

-- 2. 删除废弃列
ALTER TABLE topics DROP COLUMN slug;
ALTER TABLE topics DROP COLUMN summary;
ALTER TABLE topics DROP COLUMN status;

-- 3. 添加 view_count
ALTER TABLE topics ADD COLUMN view_count INTEGER DEFAULT 0;

-- 4. 重命名评论外键
ALTER TABLE comments RENAME COLUMN post_id TO topic_id;

-- 5. 删除旧的 likes 表，重建
DROP TABLE IF EXISTS likes;
CREATE TABLE likes (
    user_id INTEGER NOT NULL REFERENCES users(id),
    topic_id INTEGER NOT NULL REFERENCES topics(id),
    PRIMARY KEY (user_id, topic_id)
);

-- 6. 删除 post_tags 和 tags
DROP TABLE IF EXISTS post_tags;
DROP TABLE IF EXISTS tags;

-- 7. 新建 notifications 表
CREATE TABLE notifications (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    type VARCHAR NOT NULL DEFAULT 'reply',
    topic_id INTEGER REFERENCES topics(id) ON DELETE CASCADE,
    comment_id INTEGER REFERENCES comments(id) ON DELETE CASCADE,
    is_read BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 8. users 扩展
ALTER TABLE users ADD COLUMN topic_count INTEGER DEFAULT 0;
ALTER TABLE users ADD COLUMN comment_count INTEGER DEFAULT 0;

COMMIT;
```

### 博客 → 论坛的变更

| 变更 | 说明 |
|------|------|
| `posts → topics` | 表重命名。博客叫"文章"，论坛叫"话题" |
| `comments.post_id → topic_id` | 评论的外键跟着改名，保持语义一致 |
| 删除 slug, summary, status | 博客需要 SEO 友好的 URL 别名、摘要和发布状态（草稿/发布），论坛不需要 |
| 新增 view_count | 论坛需要浏览量统计 |
| 重建 likes | 旧表关联 `posts`，重建为关联 `topics` |
| 删除 post_tags, tags | blog 阶段的标签/分类系统，改造时一并清掉了 |
| 新增 notifications | 论坛需要通知（有人回复你） |
| 新增 topic_count, comment_count | 用户主页显示统计数字 |

几点值得注意：

- **整段包在 `BEGIN; ... COMMIT;` 里** —— 一次事务执行，中途出错全部回滚，不会留下改了一半的库
- **文件头的 WARNING 很诚实** —— 它明确告诉执行者"会清空 likes/post_tags/tags，只保留用户账号"。这类不可逆脚本就该把破坏性写在最显眼的地方
- **它是"一次性档案"** —— 对一个**全新**的库跑这个脚本会立刻失败（没有 `posts` 表可 rename）。它记录的是"当时那个特定的旧库怎么变成新库"，不是可重复执行的通用脚本

### ⚠️ 一个必须纠正的过时印象

看到第 6 步 `DROP TABLE IF EXISTS tags`，很容易得出"这个项目没有标签系统"的结论。**这是错的。**

标签系统确实在那次改造中被删掉了，但**后来又作为新功能重新加了回来**（模型里的 `Tag` 类和 `topic_tags` 关联表，见第二章）。所以当前代码库里：

- **标签表完整存在**：`tags`（name / slug / created_at）+ `topic_tags`（topic_id / tag_id）
- **`GET /api/tags` 接口完整存在**：返回所有标签及各自帖子数
- 发帖、改帖都支持传标签（`TopicCreate.tags` / `TopicUpdate.tags`），列表页也支持按标签筛选

阅读老资料（包括本教程的旧版本、以及仓库里其它历史文档）时，凡是看到"标签表已删除""标签接口已移除"之类的说法，都要按**当前代码**为准——它们描述的是那次改造当时的瞬时状态，而不是今天。

## 当前的迁移手段：ensure_schema()

日常的 schema 演进完全靠 `database.py` 里的 `ensure_schema()`，它在服务启动时被调用（见第二章）：

```python
def ensure_schema():
    """Create tables and apply lightweight migrations."""
    try:
        with engine.begin() as conn:
            conn.execute(text("GRANT CREATE ON SCHEMA public TO CURRENT_USER"))
    except Exception:
        logging.getLogger("blog").warning("无法在 public schema 上授权 CREATE，跳过")

    Base.metadata.create_all(bind=engine)

    with engine.begin() as conn:
        conn.execute(text(
            "ALTER TABLE comments ADD COLUMN IF NOT EXISTS parent_id INTEGER REFERENCES comments(id)"
        ))
        conn.execute(text(
            "ALTER TABLE topics ADD COLUMN IF NOT EXISTS is_pinned BOOLEAN DEFAULT FALSE"
        ))
        conn.execute(text(
            "ALTER TABLE topics ADD COLUMN IF NOT EXISTS is_featured BOOLEAN DEFAULT FALSE"
        ))
```

它靠两个机制的配合来演进 schema：

1. **`Base.metadata.create_all()`** —— 对**不存在**的表执行 `CREATE TABLE`；已存在的表原样跳过。所以新加一张表（比如当初加 `messages`、`tags`）时，只要在 `models.py` 里定义好类，下次启动就自动建出来了
2. **`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`** —— 给**已存在**的表补上后加的列。之所以单独手写这三条，是因为 `create_all` 只建表、**不会给已有的表加新列**。评论的 `parent_id`、帖子的 `is_pinned` / `is_featured` 都是后来才加的功能，老库需要靠这三条补上

## ensure_schema() 的能力边界

这个方案简单、零配置、启动即生效，但它的局限必须心里有数：

| 操作 | ensure_schema 支持？ | 说明 |
|------|:---:|------|
| 建新表 | ✅ | `create_all()` 自动完成 |
| 加新列 | ✅ | 需手写 `ADD COLUMN IF NOT EXISTS` |
| 删列 | ❌ | 没有对应语句，得手工写 SQL |
| 改列名 | ❌ | 同上 |
| 改列类型 | ❌ | 同上，且需要处理数据转换 |
| 加约束/索引（对已有表） | ❌ | `create_all` 不会补索引 |
| 数据迁移（搬数据、填默认值） | ❌ | 完全不管 |
| 回滚（downgrade） | ❌ | 没有版本概念，无法退回上一版 |

换句话说：**它只解决"往前加"这一类问题**。一旦需要"删/改/搬"，就得像 `001_blog_to_forum.sql` 那样，自己写一个一次性 SQL 脚本，部署时人工执行。

### 为什么没有引入 Alembic？

Alembic 是 SQLAlchemy 官方的迁移工具，能自动生成迁移脚本、支持 upgrade/downgrade、记录版本。它很强大，但引入它意味着：

- 多一层配置文件（`alembic.ini`、`versions/` 目录）
- 每次改模型都要"生成迁移 → 人工检查生成的 SQL → 提交 → 部署时执行"的流程
- 团队协作时必须保证所有人的迁移脚本按顺序合并

对一个个人维护、单实例部署的小论坛来说，这套流程的成本大于收益。`ensure_schema()` 用几十行代码覆盖了 90% 的实际场景（"我要加个字段/加张表"），把剩下 10% 的复杂改造留给一次性 SQL 脚本手工处理——这是一次清醒的取舍，而不是偷懒。

也有它的代价：**所有"加列"都必须手工维护一份 ALTER 列表**。如果加了新字段却忘了往 `ensure_schema()` 里补一条，本地新库（`create_all` 时字段就在 `CREATE TABLE` 里）一切正常，**只有老库会缺列**，直到线上报 `column does not exist` 才发现。写新功能时记得同步这一步。

## 本章要点

- 仓库里的 `001_blog_to_forum.sql` 是**历史一次性脚本**，记录 blog→forum 改造，不是日常迁移手段，新库不要跑它
- 那次改造删过 `tags`，但标签系统**后来又加回来了**：`tags` / `topic_tags` 表和 `GET /api/tags` 都完整存在
- 当前 schema 演进靠 `ensure_schema()`：`create_all()` 建表 + 手写 `ADD COLUMN IF NOT EXISTS` 加列
- `ensure_schema()` **只能加，不能删/改名/改类型**，也处理不了数据迁移和回滚
- 项目**没有 Alembic**，复杂改造用一次性 SQL 脚本手工执行——是权衡后的选择
- 隐患：新增字段时别忘了同步 `ensure_schema()` 的 ALTER 列表，否则只有老库会缺列
