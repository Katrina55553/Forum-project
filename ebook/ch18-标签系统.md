# 第十八章：标签系统

前十七章每个功能各占一张表：帖子在 `topics`，评论在 `comments`。标签不同——它是本项目里**唯一一处真正的多对多设计**，也是理解关联表最好的一课。

顺带交代一段背景：项目原本是博客，`8b8ef89`（05-15）改成论坛的那次重构顺手删掉了 `Tag`，`b7beb27`（05-28）又以多对多形式加了回来。因为删标签的理由"论坛初期用不上"在实际使用中站不住：没有标签，帖子列表只剩"按时间倒序"一种组织方式，几十篇之后就没法逛了。而加回来不是贴回旧代码，是重新设计——从"帖子表里一个分类字符串"变成"独立 `tags` 表 + 关联表"。

## 1. 分类 vs 标签：一对多还是多对多

这两个概念看着像，数据模型却完全不同：

```
分类（一对多，排他）                    标签（多对多，可叠加）
一篇帖子 属于 一个分类                  一篇帖子 有 多个标签
一个分类 包含 多篇帖子                  一个标签 属于 多篇帖子
posts.category_id = 3                  post_tags: (1,2) (1,5) (3,2) ...
```

分类是"要么技术、要么生活"的二选一，在主表加一个 `category_id` 字段就够。标签是可叠加的：一篇讲 FastAPI 的帖子可以同时是 `#Python`、`#后端`、`#FastAPI`。多对多必须在数据库层面引入**第三张关联表**：

```
     topics                 topic_tags               tags
┌──────────────┐      ┌──────────────────┐    ┌──────────────┐
│ id           │◄─────│ topic_id  (PK)   │    │ id           │
│ title        │      │ tag_id    (PK)   │───►│ name  unique │
│ author_id    │      └──────────────────┘    │ slug  unique │
└──────────────┘   帖子 1 有标签 2、5 → (1,2) (1,5) 两行  └──────────────┘
```

`topic_tags` 本身没有内容，只存两列外键，这类表叫**联结表 / 中间表**。

## 2. 后端模型：Tag 与 topic_tags

对应 `backend/models.py`：

```python
class Tag(Base):
    __tablename__ = "tags"

    id = Column(Integer, primary_key=True, index=True)
    name = Column(String, unique=True, nullable=False, index=True)
    slug = Column(String, unique=True, nullable=False, index=True)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))


# topic_tags table for Topic.tags relationship
topic_tags = Table(
    "topic_tags",
    Base.metadata,
    Column("topic_id", Integer, ForeignKey("topics.id"), primary_key=True),
    Column("tag_id", Integer, ForeignKey("tags.id"), primary_key=True),
)
```

`Topic` 里对应一行：

```python
    likes = relationship("User", secondary="likes")          # 点赞：User ↔ Topic 的多对多
    tags = relationship("Tag", secondary="topic_tags")        # 标签：Topic ↔ Tag 的多对多
```

三个要点：

**① 为什么用 `Table` 而不是 `class`？** 因为 `topic_tags` 除了两列外键什么都没有。SQLAlchemy 对纯联结表提供了简写：`Table(...)` 挂在 `Base.metadata` 上即可，不必声明成类。将来若要给关联加额外信息（比如"什么时候打上的标签"），才需要升级成真正的模型类。

**② 两列都 `primary_key=True`，这叫复合主键**，含义是"两列合起来唯一"，不是各自唯一：

```
允许：(1,2) (1,5) (3,2)     ← topic_id=3 再次出现没问题
禁止：重复插入 (1,2)         ← 主键冲突，数据库直接拒绝
```

于是"同一篇帖子不能重复打同一标签"这条规则**不需要写代码查重，数据库层面就保证了**——和第四章点赞把约束交给数据库是同一招。区别在于：重复点赞是用户真会做的事（手抖连点），所以要捕获 `IntegrityError`；而重复标签在前端 `TagInput` 就被拦住了，后端不需要容错。

**③ `secondary="topic_tags"`** 告诉 SQLAlchemy：`topic.tags` 是通过中间表查 `tags`，于是可以直接用对象读写，不用手写 SQL：

```python
topic.tags = [tag1, tag2]     # SQLAlchemy 自动往 topic_tags 插两行
for t in topic.tags:          # 读取
    print(t.name)
```

## 3. slug：给标签一个"URL 用的名字"

`Tag` 表里 `name` 和 `slug` 看着重复，其实是分工：

```
name = "Machine Learning"      ← 给人看的
slug = "machine-learning"      ← 给 URL 和查询用的
```

只用 `name` 的话筛选链接会变成 `/?tag=Machine%20Learning`（空格转义，难看易错）；用 slug 则是干净的 `/?tag=machine-learning`。生成规则只有一行（在 `crud.get_or_create_tags` 里）：

```python
slug = name.lower().replace(" ", "-")
```

**但这套规则是为英文设计的，对中文标签几乎不起作用。** 中文没有大小写，`lower()` 是空操作；中文标签通常也不打空格。所以 `#前端` 的 slug 就是 `前端` 本身：

| 输入 | `lower()` 后 | 最终 slug |
|------|-------------|----------|
| `FastAPI` | `fastapi` | `fastapi` |
| `Machine Learning` | `machine learning` | `machine-learning` |
| `前端` | `前端` | `前端` |
| `机器 学习` | `机器 学习` | `机器-学习` |

**这不算 bug，是"够用就好"的取舍**：好处是零依赖、一行代码；代价是做不到"中文标签转拼音 URL"。真要严格化可以"中文回退成 `tag-{id}`"或引入拼音库，但链接可读性反而下降。保持简单是这个项目一贯的选择。

## 4. 数据层：四个关键实现

### 4.1 `get_or_create_tags`：先查后建

发帖时用户输入的是一串字符串（`["Python", "后端"]`），数据库要的是 `Tag` 对象，转换靠它：

```python
def get_or_create_tags(db: Session, tag_names: list[str]) -> list[Tag]:
    """获取或创建标签，返回 Tag 对象列表"""
    tags = []
    for name in tag_names:
        name = name.strip()
        if not name:
            continue
        slug = name.lower().replace(" ", "-")
        tag = db.query(Tag).filter_by(slug=slug).first()
        if not tag:
            tag = Tag(name=name, slug=slug)
            db.add(tag)
            db.flush()
        tags.append(tag)
    return tags
```

- `name.strip()` + `if not name: continue`：跳过空标签，防前端传来 `["", " "]` 这种脏数据。
- **按 `slug` 查重而不是按 `name`**：按 name 查的话，`FastAPI` 和 `fastapi` 会被当成两个标签建出来，第二个插入时撞 `slug` 唯一约束报错；按 slug 查，`FastAPI` 会复用已有的 `fastapi` 标签（显示名仍是先创建时那个）。
- **用 `db.flush()` 而不是 `db.commit()`**：`flush()` 把 SQL 发给数据库执行但不开新事务，`commit()` 则提交并结束事务。这里必须 flush，因为后面 `create_topic` 还要把 topic 和这些 tags 一起提交。若在此 commit，就拆成两次事务，中途失败会留下"标签建好但帖子没建"的脏数据。**一次操作一个事务。**

### 4.2 `get_all_tags`：统计每个标签有多少帖子

```python
def get_all_tags(db: Session) -> list[dict]:
    """获取所有标签及其帖子数量"""
    rows = (
        db.query(Tag, func.count(topic_tags.c.topic_id).label("count"))
        .outerjoin(topic_tags, Tag.id == topic_tags.c.tag_id)
        .group_by(Tag.id)
        .order_by(func.count(topic_tags.c.topic_id).desc())
        .all()
    )
    return [{"id": t.id, "name": t.name, "slug": t.slug, "count": c} for t, c in rows]
```

目标是拿到 `[{name: "前端", slug: "前端", count: 12}, ...]` 渲染首页标签栏。核心问题是"怎么数出每个标签挂了多少帖子"，答案三步：`outerjoin` → `group_by` → `count`。

**为什么必须是 `outerjoin`（左外连接）而不是 `join`（内连接）？** 内连接只保留两边都能匹配的行，于是**没有任何帖子的标签会被整行丢掉**，`#Rust` 这类新标签会从页面上消失。左外连接保留左表（`tags`）的所有行，匹配不上就填 `NULL`，`count` 为 `0`。业务上的差别很实在：用户刚建了一个标签还没发帖，前端得能看见它、确认"建成功了"。

两个细节：`func.count(topic_tags.c.topic_id)` 数的是 `topic_id`（因为 `group_by(Tag.id)` 已按标签分组，数谁都一样）；`.order_by(...desc())` 让热门标签排前面。这里**没有分页也没有截断**，标签极多时接口返回体偏大，属于可接受的简化。

> 通用写法：`outerjoin` + `group_by` + `count` 是"统计主表里每行有多少个从属记录"的标准套路。

### 4.3 按标签筛选：`Topic.tags.any()` 生成 EXISTS

筛选藏在 `get_topics` 里，**计数查询和取数查询各写一遍**：

```python
if tag:
    count_query = count_query.filter(Topic.tags.any(Tag.slug == tag))
...
if tag:
    query = query.filter(Topic.tags.any(Tag.slug == tag))
```

`Topic.tags.any(...)` 翻译成 SQL 大致是：

```sql
SELECT * FROM topics
WHERE EXISTS (
    SELECT 1 FROM topic_tags JOIN tags ON tags.id = topic_tags.tag_id
    WHERE topic_tags.topic_id = topics.id AND tags.slug = 'frontend'
)
```

**为什么不用 join 来筛？** 在"一篇帖子恰好一个标签"时两者没区别，但如果筛选条件变成"带 A 标签**或** B 标签"，join 会让同一篇帖子出现好几行（每个匹配标签一行），结果列表出现重复帖子、计数也跟着膨胀。`EXISTS` 天然只判断"存不存在"，每篇帖子最多出现一次，**语义更准且不会重复**。

### 4.4 写入：创建与更新

```python
def create_topic(db, author_id, title, content, tag_names=None) -> Topic:
    topic = Topic(title=title, content=content, author_id=author_id)
    db.add(topic)
    if tag_names:
        tags = get_or_create_tags(db, tag_names)
        topic.tags = tags
    db.query(User).filter_by(id=author_id).update({"topic_count": User.topic_count + 1})
    db.commit()
    db.refresh(topic)
    return topic
```

```python
def update_topic(db: Session, topic: Topic, data: dict) -> Topic:
    for field in ("title", "content"):
        if data.get(field) is not None:
            setattr(topic, field, data[field])
    if "tags" in data and data["tags"] is not None:
        tags = get_or_create_tags(db, data["tags"])
        topic.tags = tags
    db.commit()
    db.refresh(topic)
    return topic
```

`topic.tags = tags` 看着平平无奇，实际会**先清空这篇帖子的旧关联、再插入新的关联**，所以编辑时整体赋值即可，不用自己算"哪些新增、哪些删除"。

`update_topic` 里的两个判断缺一不可：`"tags" in data` 表示请求里提到了 tags 字段，`data["tags"] is not None` 排除显式传 `tags: null`。**只有明确传 `tags: []`（空数组）才会清空标签**——这是"部分更新"（partial update）的标准写法，因为路由层用的是 `data.model_dump(exclude_unset=True)`。

## 5. 接口层：一个公开端点，和一处不一致

标签唯一公开端点是 `GET /api/tags`：

```python
@app.get("/api/tags")
def list_tags(db: Session = Depends(get_db)):
    return get_all_tags(db)
```

注意它**没有 `current_user` 依赖**，未登录也能访问——首页标签栏对游客同样展示。对比 `GET /api/notifications` 必须登录：**认证加在哪一层，取决于数据是不是私有。**

发帖/编辑沿用已有端点，通过 body 的 `tags` 字段携带：

| 端点 | 方法 | 认证 | `tags` 相关行为 |
|------|------|------|---------------|
| `/api/tags` | GET | 公开 | 返回 `[{id, name, slug, count}]` |
| `/api/topics` | POST | 需登录 | body 支持 `tags: list[str]` |
| `/api/topics/{id}` | PUT | 作者或管理员 | body 支持 `tags`，整体覆盖 |
| `/api/topics/{id}/edit` | GET | 作者或管理员 | ⚠️ **不返回 tags** |

### ⚠️ 一处真实存在的接口不一致

编辑页要把帖子现有标签回填到 `TagInput`，于是调 `GET /api/topics/{id}/edit`：

```python
@app.get("/api/topics/{topic_id}/edit")
def get_topic_for_edit_route(topic_id: int, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    topic = get_topic_for_edit(db, topic_id)
    if not topic:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Topic not found")
    _author_or_admin(topic, current_user)
    return {"id": topic.id, "title": topic.title, "content": topic.content}
```

返回的字典**只有 id/title/content 三个键，没有 tags**。而前端是这么写的：

```javascript
const res = await getTopicForEdit(route.params.id);
title.value = res.data.title;
content.value = res.data.content;
tags.value = res.data.tags?.map(t => t.name) || [];
```

`res.data.tags` 永远是 `undefined`，于是 `tags.value` 永远是 `[]`。**后果**：编辑一个原本带 `#Python #后端` 的帖子时，标签框是空的；用户没注意直接保存，`update_topic` 收到 `tags: []` 会把原有标签**全部清空**。

修法二选一：

```python
# 方案 A：edit 接口把标签一起返回
return {
    "id": topic.id, "title": topic.title, "content": topic.content,
    "tags": [{"id": t.id, "name": t.name, "slug": t.slug} for t in topic.tags],
}
```

```javascript
// 方案 B：前端编辑页改用 getTopicById（详情接口本来就返回 tags）
const res = await getTopicById(route.params.id);
```

方案 A 更直接，但 `get_topic_for_edit` 目前在 crud 层只 `joinedload(Topic.author)`，没有加载 `tags`，需要补上 `joinedload(Topic.tags)`，否则会多一次懒加载查询（N+1 的小变体）。

**这个案例的价值不在于修 bug，而在于提醒你**：一个字段从"只在详情页显示"变成"也要在编辑页回填"时，**所有相关的读接口都要一起检查**。接口返回结构不一致，是前后端分离项目里最常见的一类隐性 bug——它不报错，只是安静地给你一个空值。

## 6. 前端 `TagInput.vue`：一个标准的 v-model 组件

用法很简单：

```html
<TagInput v-model="tags" :suggestions="allTags" />
```

一行 `v-model` 就把父组件的 `tags` 数组交给子组件管理，拆开看只有两个约定：

```
父组件 TopicEditView.vue                     子组件 TagInput.vue
│ tags = ["Python"]      │── prop(modelValue) ──►│ props.modelValue
│ tags = ["Python","X"]  │◄─ event ─────────────│ emit("update:modelValue", […])
```

- **下行用 prop**：固定名 `modelValue`
- **上行用 event**：固定名 `update:modelValue`

`v-model="tags"` 只是 `:model-value="tags" @update:model-value="tags = $event"` 的语法糖，所以子组件声明必须严格对上：

```javascript
const props = defineProps({
  modelValue: { type: Array, default: () => [] },
  suggestions: { type: Array, default: () => [] },
});

const emit = defineEmits(["update:modelValue"]);
```

注意 `default: () => []`——**数组/对象的默认值必须写成工厂函数**。写成 `default: []` 的话所有组件实例会共享同一个数组，一个输入框里加标签会莫名其妙地出现在另一个输入框里。

子组件维护一份本地副本 + `watch` 同步：

```javascript
const input = ref("");
const tags = ref([...props.modelValue]);

watch(() => props.modelValue, (val) => {
  tags.value = [...val];
});
```

**为什么不直接用 `props.modelValue`？** 因为 Vue 的一条铁律：子组件不能直接修改 props。子组件维护本地 `tags` 用来渲染，改动时 `emit` 通知父组件，父组件改了 `modelValue`，`watch` 再把新值同步回来，形成闭环。`[...val]` 是浅拷贝，用来**断开引用**、避免互相污染。那个 `watch` 的作用是响应外部变化——父组件异步加载完把 `tags` 从 `[]` 换成 `["Python","后端"]` 时，输入框要跟着显示出来。

添加、删除与键盘交互：

```javascript
function addTag(name) {
  name = name.trim();
  if (!name || tags.value.includes(name)) {   // 空输入忽略 + 去重（前端先拦一道）
    input.value = "";
    return;
  }
  tags.value.push(name);
  emit("update:modelValue", tags.value);
  input.value = "";
}

function removeTag(index) {
  tags.value.splice(index, 1);
  emit("update:modelValue", tags.value);
}

function onKeydown(e) {
  if (e.key === "Enter" || e.key === ",") {          // 回车 / 逗号确认
    e.preventDefault();
    addTag(input.value);
  }
  if (e.key === "Backspace" && !input.value && tags.value.length) {
    tags.value.pop();                                // 输入框空时退格删最后一个
    emit("update:modelValue", tags.value);
  }
}
```

删除用 `splice(index, 1)` 按下标删，因为模板里 `v-for` 本来就给了 `index`，不用再 `indexOf` 找。`Backspace` 那行**必须判断 `!input.value`**：否则用户打字时按退格想删一个字符，会把整个标签删掉。`e.preventDefault()` 加在 Enter/逗号上，是因为这两个键有默认行为（表单提交、光标移动）。

热门标签建议点一下就直接加进去：

```javascript
function addSuggestion(tag) {
  if (!tags.value.includes(tag.name)) {
    tags.value.push(tag.name);
    emit("update:modelValue", tags.value);
  }
}
```

模板用 `:class="{ active: tags.includes(tag.name) }"` 让已选中的建议变成实心主色。**注意比较的是 `tag.name` 而不是 `tag.slug`**——因为 `tags` 数组里存的就是标签名（提交给后端的也是 `list[str]`）。

## 7. 首页：把筛选状态放进 URL

标签功能在前端最精彩的地方在 `HomeView.vue` 的状态设计：

```javascript
const currentTag = computed(() => route.query.tag || "");

function filterByTag(slug) {
  page.value = 1;
  const query = { ...route.query };
  if (slug === currentTag.value) {
    delete query.tag;              // 再点一次已选中的 = 取消筛选
  } else {
    query.tag = slug;
  }
  router.push({ name: "home", query });
}
```

`filterByTag` **不发任何请求**，它只改 URL：URL 变成 `/?tag=前端` → `watch` 监听到 `route.query` 变化 → `fetchTopics()` → `GET /api/topics?tag=前端`。再点一次当前标签就是"取消筛选"，所以标签栏里的按钮既是"选中"也是"取消"。

**为什么筛选状态要放在 URL 里？** 关键在这一行是 `computed` 而不是 `ref`——它**从 URL 派生**，自己不做状态的唯一来源：

| 场景 | 存在组件内部 `ref` | 存在 URL（本项目） |
|------|---------------------|---------------------|
| 用户按 F5 刷新 | 筛选丢失，回到全部帖子 | 筛选保留 |
| 把链接发给朋友 | 对方看到全部帖子 | 对方看到同一筛选结果 |
| 按浏览器后退 | 什么都不发生 | 回到上一个筛选状态 |

一句话：**URL 是浏览器的公共状态栏，能被书签、分享、前进后退机制免费复用的状态，就不该藏在组件内部。** 搜索词 `q` 也用了同一套设计，所以 `/?q=FastAPI&tag=后端` 这样的组合链接能直接分享给别人。

一个容易被忽略的 watch 细节：

```javascript
watch(page, fetchTopics);
// query 变化时只重置 page，由 page watcher 触发 fetchTopics，避免双重请求竞态
watch(() => route.query, () => {
  if (page.value !== 1) {
    page.value = 1;
  } else {
    fetchTopics();
  }
}, { deep: true });
```

如果直接写 `page.value = 1; fetchTopics();`，用户在**第 3 页**点标签筛选时，`page.value = 1` 会先触发 `page` watcher 发一次请求，紧接着又发一次——两个并发请求谁先返回不确定，后返回的覆盖前者，列表内容可能错乱。现在的写法保证**同一个动作永远只产生一个请求**。结论：**当两个 watch 可能被同一个原因触发时，要显式决定由谁负责发请求。**

详情页的标签是 `router-link`，直接指向首页并带上 query：

```html
<router-link :to="{ name: 'home', query: { tag: tag.slug } }" class="topic-tag">
  #{{ tag.name }}
</router-link>
```

用对象形式的 `:to`（而不是拼字符串）有两个好处：`name: "home"` 让路由变了 URL 也自动跟随；`query` 里的值会被 Vue Router 自动编码，中文标签不用手动转义。点一下就回到上面的流程，整个链路上**没有任何一处需要"记住当前筛选"的全局状态**，一切都从 URL 推导。

## 本章要点

- 分类是一对多（排他），标签是多对多（叠加）；多对多需要第三张关联表 `topic_tags`
- 标签被删过又重新设计：`8b8ef89`（05-15）删掉 `Tag`，`b7beb27`（05-28）以多对多形式加回
- `topic_tags` 用 `Table(...)` 而非模型类，因为只有两列外键；两列都 `primary_key=True` 构成**复合主键**，数据库层保证不重复
- `Topic.tags = relationship("Tag", secondary="topic_tags")`；`topic.tags = new_list` 会先清旧关联再插新的
- `slug` 是给 URL 用的名字，规则 `name.lower().replace(" ", "-")`；**对中文标签不起作用**（中文无大小写、无空格），是有意保留的简化
- `get_or_create_tags` 按 slug 查重、用 `flush()` 而非 `commit()`，把建标签和建帖子合到同一事务
- `get_all_tags` 用 **`outerjoin` + `group_by` + `count`**：用 `join` 的话，没有帖子的标签会被整行丢掉
- 按标签筛选用 `Topic.tags.any(Tag.slug == tag)`（生成 `EXISTS`），比 `join` 更准、不会产生重复行
- `GET /api/topics/{id}/edit` **不返回 `tags`**，导致编辑页标签回填为空、保存时会清空原标签——一处真实的接口不一致
- `TagInput` 是标准 **v-model 组件**：`modelValue` prop 下行 + `update:modelValue` 事件上行；子组件不能改 props，故维护本地副本 + `watch` 同步；数组默认值必须写成工厂函数
- 首页把筛选状态存在 **`route.query.tag`**（`computed` 从 URL 派生），刷新、分享链接、浏览器后退都能保留筛选
- 两个 watch 可能被同一动作触发时，要显式指定"由谁负责发请求"，避免重复请求与竞态
