# 第十九章：私信与统一收件箱

本章讲项目里逻辑最绕的一块：私信。绕的原因不是功能复杂（"发一条消息给某人"听起来简单极了），而是**数据库里根本没有"会话"这个东西**——所有会话列表、未读数、对话内容，都是从 `messages` 一张表里"算"出来的。

第十七章已从页面的角度讲过 `MessagesView` 和 `ChatView`，本章换个角度：站在数据库和接口设计的位置，把"为什么必须这么绕"讲透，并补上几个前章没说清的坑。

先交代一段历史。`67842c3` 加了私信系统，当天 `6ae6ea4` 就**把通知和私信合并成一个页面**——因为对用户来说，"有人回复了你的帖子"和"有人给你发了条消息"是同一种体验：有人找你。合并后 `/notifications` 变成 `redirect` 到 `/messages`；`NotificationsView.vue` 这个文件还在仓库里，但**没有路由指向它、也没有任何地方 import 它**，是架构演进留下的**死代码**。

## 1. `Message` 模型：一张表两次指向 users

```python
class Message(Base):
    __tablename__ = "messages"

    id = Column(Integer, primary_key=True, index=True)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    receiver_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    is_read = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

    sender = relationship("User", foreign_keys=[sender_id])
    receiver = relationship("User", foreign_keys=[receiver_id])

    __table_args__ = (
        Index("ix_messages_sender_receiver", "sender_id", "receiver_id"),
        Index("ix_messages_receiver_read", "receiver_id", "is_read"),
    )
```

字段没什么特别，**重点是那两行 `relationship`**。按直觉写成 `sender = relationship("User")` / `receiver = relationship("User")`，第一次用到它们时 SQLAlchemy 会抛：

```
AmbiguousForeignKeysError: Could not determine join condition between parent/child
tables on relationship Message.sender - there are multiple foreign key paths
linking the tables.  Specify the 'foreign_keys' argument...
```

翻译："`messages` 到 `users` 有两条外键路径（`sender_id`、`receiver_id`），你想让我用哪条？"这不是笨，恰恰相反——**它拒绝猜**。如果它自作主张挑了 `sender_id`，那么查 `receiver` 时会拿到完全错误的数据，而且不报错。**宁可启动时炸掉，也不要运行时静默给错数据。**

修法就是显式点名（注意是 `[sender_id]` 这样的**列表**，不是 `sender_id` 本身）：

```python
sender = relationship("User", foreign_keys=[sender_id])
receiver = relationship("User", foreign_keys=[receiver_id])
```

**识别信号：只要一张表里有两个或更多指向同一张表的外键，就必须给 `relationship` 加 `foreign_keys`。** 同类场景还有好友关注、订单买卖双方。项目里 `Message` 是唯一命中这个坑的表——`Comment` 的 `topic_id` 和 `user_id` 指向不同的表，没有歧义，所以不需要 `foreign_keys`。

## 2. 两个复合索引，分别服务两种查询

```python
__table_args__ = (
    Index("ix_messages_sender_receiver", "sender_id", "receiver_id"),
    Index("ix_messages_receiver_read", "receiver_id", "is_read"),
)
```

索引不是"加了就好"，而是**按查询模式加**：`(sender_id, receiver_id)` 服务"我发给他的所有消息"→ 双向对话；`(receiver_id, is_read)` 服务"他发给我的未读消息"→ 未读计数与角标。

**列顺序很关键**，最左前缀原则决定一切：`(receiver_id, is_read)` 能加速 `WHERE receiver_id = 1 AND is_read = false`；若写成 `(is_read, receiver_id)` 就差很多——`is_read` 基数太低（只有两个值），布尔列放最左会让索引几乎退化成"只筛掉一半数据"的普通索引。**结论：等值查询的列放前面，且尽量把区分度高的列放左边。**

> `is_read` 这类状态位索引还有天然局限：**已读消息会一直累积**，索引选择性随时间变差。项目规模不大时不用管；数据量真的大了，"已读消息归档到历史表"才是正解。知道这个局限比知道索引怎么加更重要。

## 3. `send_message`：最少逻辑的一个函数

```python
def send_message(db: Session, sender_id: int, receiver_username: str, content: str) -> Message | None:
    receiver = db.query(User).filter_by(username=receiver_username).first()
    if not receiver or receiver.id == sender_id:
        return None
    message = Message(sender_id=sender_id, receiver_id=receiver.id, content=content)
    db.add(message)
    db.commit()
    db.refresh(message)
    return message
```

关键在返回值的设计：**失败时返回 `None`，而不是抛异常**。它挡掉两种情况——收件人不存在、给自己发消息。两者业务性质完全不同（"对方不存在" vs "你不该这么做"），却合并成同一个 `None`，靠的是分层职责：**数据层不关心 HTTP**，所以用最简单的 `None` 表示失败；**路由层负责翻译成 HTTP**：

```python
@app.post("/api/messages")
@limiter.limit("10/minute")
def send_message_route(request: Request, data: MessageCreate, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    message = send_message(db, current_user.id, data.receiver, sanitize(data.content))
    if not message:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="发送失败，用户不存在或不能给自己发私信")
    return {"message": "发送成功", "id": message.id}
```

两个安全细节：`sanitize(data.content)` 和帖子、评论用同一个 `bleach` 白名单——**私信内容最后要渲染到对方页面上，XSS 风险一模一样，不能因为是"私密"就跳过净化**；`@limiter.limit("10/minute")` 限流，私信最容易被用来刷屏骚扰，额度比发帖更严，因为一条消息的"成本"低得多。对外参数用**用户名**而不是 id，让请求体对人可读（`{receiver: "alice"}` 比 `{receiver: 7}` 友好），代价是每次多一次 `filter_by(username=...)` 查询。

## 4. `get_conversations`：本章最难的一段

### 4.1 问题：没有会话表

微信、Telegram 通常有一张 `conversations` 表记录"谁和谁在聊、最后一条、未读数"。这个项目**没有**，只有一张扁平的消息表，每行是 `(id, sender_id, receiver_id, is_read, content)`。而前端要的却是 `(username, last_message, last_message_at, unread)` 这样的列表。所以**"会话"必须从消息里推算**，核心就一句话：对每条和我有关的消息，`我发的 → 对方 = receiver_id`；`别人发的 → 对方 = sender_id`。

### 4.2 子查询一：对方是谁 + 每个会话的最新一条

```python
latest_sq = (
    db.query(
        case(
            (Message.sender_id == user_id, Message.receiver_id),
            else_=Message.sender_id
        ).label("other_id"),
        func.max(Message.id).label("last_msg_id"),
    )
    .filter(or_(Message.sender_id == user_id, Message.receiver_id == user_id))
    .group_by("other_id")
    .subquery()
)
```

三段分别看：

**① `case(...)` 是 SQL 里的 if/else**，SQLAlchemy 2.0 的新写法是"传一堆 `(条件, 值)` 元组，最后 `else_=` 兜底"（如上所示：我发的取 `receiver_id`，否则取 `sender_id`）。翻译成 SQL 就是 `CASE WHEN messages.sender_id = 1 THEN messages.receiver_id ELSE messages.sender_id END AS other_id`。给 alice 算一遍：

| 消息 | sender | receiver | 我发的？ | → `other_id` |
|:---:|:---:|:---:|:---:|:---:|
| 7 | 1 | 2 | 是 | **2**（bob） |
| 9 | 2 | 1 | 否 | **2**（bob） |
| 11 | 1 | 3 | 是 | **3**（carol） |
| 15 | 2 | 1 | 否 | **2**（bob） |

`other_id` 一算出来，"谁是会话对象"就变成了普通的 `GROUP BY`。

**② `func.max(Message.id)` 取每个会话的最新一条**：按 `other_id` 分组后取组内最大 id——`other_id=2` 组 `{7,9,15}` → 15，`other_id=3` 组 `{11}` → 11。于是每个会话只剩一行 `(other_id, last_msg_id)`。

> 隐含假设：用 `max(id)` 代表"最新"，前提是 **id 自增且顺序与时间一致**。更稳妥的写法是"按 `created_at` 倒序取第一条"，代价是 SQL 复杂得多。项目选了 `max(id)`，属于**利用主键单调性的简化**——够用，但要意识到前提。另外 `.group_by("other_id")` 传的是**字符串**而不是 label 对象：因为 `case(...)` 的结果没有变量名可引用，SQLAlchemy 支持用字符串引用同一 SELECT 里已定义的 label。

**③ `.filter(or_(...))`** 只看和我有关的消息（"我发的"**或**"发给我的"），没有它，全站所有人的消息都会被算进来。

### 4.3 子查询二：每个会话的未读数

```python
unread_sq = (
    db.query(
        Message.sender_id.label("other_id"),
        func.count(Message.id).label("cnt"),
    )
    .filter(Message.receiver_id == user_id, Message.is_read == False)
    .group_by(Message.sender_id)
    .subquery()
)
```

比第一个简单，因为场景更窄：**未读消息必然是"别人发给我的"**，不需要 `case` 绕弯——`sender_id` 直接就是 `other_id`，顺手 `label("other_id")` 让两个子查询有**同名的列**，方便后面 join。

按上面的数据算（alice，`receiver_id = 1` 且 `is_read = false`）：符合条件的是 id 9 和 15，都是 sender 2 → `other_id = 2, cnt = 2`。carol 一条未读都没有，所以**在 `unread_sq` 里完全没有 carol 这个组**——这正是下一节必须用 `coalesce` 的原因。
### 4.4 主查询：把三份数据拼起来

```python
rows = (
    db.query(
        User.username,
        User.avatar,
        Message.content,
        Message.created_at,
        func.coalesce(unread_sq.c.cnt, 0).label("unread_count"),
    )
    .join(latest_sq, User.id == latest_sq.c.other_id)
    .join(Message, Message.id == latest_sq.c.last_msg_id)
    .outerjoin(unread_sq, unread_sq.c.other_id == User.id)
    .order_by(Message.created_at.desc())
    .all()
)
```

三个 join，各有明确理由：

**① `.join(latest_sq, User.id == latest_sq.c.other_id)`** —— 主查询的 `FROM` 是 `users`。这个 join 把 `other_id` **翻译成人**（`other_id = 2` → `username = "bob"` + 头像），同时**顺带完成过滤**：不在 `latest_sq` 里的人（和我没聊过的）自然不会出现。**"只列出聊过天的人"这个条件靠 inner join 顺带完成，不用额外写 `WHERE`。**

**② `.join(Message, Message.id == latest_sq.c.last_msg_id)`** —— 每行手里只有一个"最新消息 id"，再 join 回 `messages` 取内容和时间；这一 join 也让 `order_by(Message.created_at.desc())` 成立——**会话列表按"最后一条消息的时间"倒序**，最近聊过的排最上面。

**③ `.outerjoin(unread_sq, ...)` 必须用 `outerjoin`，不能是 `join`** —— carol 没有未读消息，`unread_sq` 里没有 `other_id = 3` 这行；用内连接的话 **carol 这个会话会整行消失**，用户会发现"聊天记录明明在，会话列表里却没有"。用 `outerjoin` 后 carol 那行的 `cnt` 是 `NULL`，于是 `func.coalesce(unread_sq.c.cnt, 0)` 兜底成 `0`（`COALESCE(a, b)` 返回第一个非 NULL 值）。

**这和第十八章 `get_all_tags` 用 `outerjoin` 完全是同一个理由**：只要"左表的行必须全部保留"，就用 `outerjoin`，并准备好在后续处理 `NULL`。

收尾：

```python
    return [
        {
            "username": r.username,
            "avatar": r.avatar or "",
            "last_message": (r.content or "")[:50],
            "last_message_at": r.created_at.isoformat() if r.created_at else "",
            "unread_count": r.unread_count or 0,
        }
        for r in rows
    ]
```

三处防御性写法：`r.avatar or ""` 兜住 `NULL`，让前端不用处理 null；`(r.content or "")[:50]` 把预览**截断到 50 字符**（表述层优化：不用把长文本传给客户端再截断）；`r.unread_count or 0` 再兜一次。**为什么返回 `dict` 而不是 ORM 对象？** 因为结果是"从三张表各取几个字段"拼出来的**投影**，不是完整模型，SQLAlchemy 返回的 `Row` 本来也不能直接序列化成 JSON。

## 5. 双向对话与"打开即已读"

```python
def get_messages_with_user(db: Session, user_id: int, other_username: str, page: int = 1, size: int = 50) -> dict | None:
    other_user = db.query(User).filter_by(username=other_username).first()
    if not other_user:
        return None

    query = db.query(Message).filter(
        or_(
            (Message.sender_id == user_id) & (Message.receiver_id == other_user.id),
            (Message.sender_id == other_user.id) & (Message.receiver_id == user_id),
        )
    )
    total = query.count()
    messages = (
        query.order_by(Message.created_at.asc())
        .offset((page - 1) * size)
        .limit(size)
        .all()
    )
    return {
        "messages": [
            {
                "id": msg.id,
                "sender_id": msg.sender_id,
                "receiver_id": msg.receiver_id,
                "content": msg.content,
                "is_read": msg.is_read,
                "created_at": msg.created_at.isoformat(),
            }
            for msg in messages
        ],
        "other_user": {"id": other_user.id, "username": other_user.username, "avatar": other_user.avatar or ""},
        "total": total,
    }
```

这条 `or_` 的语义是"**我发给他的 或 他发给我的**"，两个方向缺一不可。注意用 `&` 而不是 Python 的 `and`：`(a == 1) and (b == 2)` 会对 SQL 表达式对象做真值判断而报错。**在 SQLAlchemy 里拼条件，与用 `&`、或用 `|`、取反用 `~`，且括号不能省**（`&`/`|` 优先级高于比较运算符）。排序用 `asc()`——聊天记录从旧到新读、最新一条在底部；而会话列表是倒序。**同一个数据，两种场景、两个方向。**

返回结构 `{messages, other_user, total}` 是"复合响应"：一次请求同时给消息数组、对方信息和总数，聊天页挂载时只需一次请求就知道"对方是谁"。`other_user` 不存在时返回 `None`，路由层翻译成 404：

```python
@app.get("/api/messages/{username}")
def get_messages_route(
    username: str,
    page: int = Query(1, ge=1),
    size: int = Query(50, ge=1, le=200),
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db),
):
    result = get_messages_with_user(db, current_user.id, username, page, size)
    if not result:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="用户不存在")
    # 标记消息为已读
    mark_messages_read(db, current_user.id, username)
    return result
```

注意执行顺序：**先取数据，再标记已读**。反过来（先标记再查询）的话，返回的 `is_read` 就全是 `true` 了。`size` 用 `Query(50, ge=1, le=200)` 限制上限，防止有人传 `size=999999` 把数据库拖慢。

`mark_messages_read` 只标记"**他发给我的**"消息，用 `query.update()` 生成**一条 `UPDATE ... WHERE`**（而不是查出来逐条改、生成 N 条 update）——**批量更新走 SQL 层，是 ORM 里最容易拿到的性能红利**。`get_unread_message_count` 则是全局未读总数，服务导航栏角标：它和 `unread_sq` 算的是同一件事，区别是前者要**按人分组**（每行显示自己的未读数）、后者要**总数**。同一个业务概念、两种聚合粒度、两段 SQL——**不要为了让代码"看起来复用"而硬把两者糅成一个函数**，它们的读取模式和索引需求都不同。

## 6. 五个端点，和一个必须记住的声明顺序

| # | 端点 | 方法 | 认证 | 限流 | 说明 |
|---|------|------|:----:|:----:|------|
| 1 | `/api/messages` | POST | 需登录 | 10/min | body `{receiver, content}`，失败返回 400 |
| 2 | `/api/messages` | GET | 需登录 | — | 会话列表（`get_conversations`） |
| 3 | `/api/messages/unread-count` | GET | 需登录 | — | `{count: n}`，导航栏角标用 |
| 4 | `/api/messages/{username}` | GET | 需登录 | — | 双向对话，**读取后自动标记已读** |
| 5 | `/api/messages/{username}/read` | PUT | 需登录 | — | 手动标记已读 |

五个端点**全部需要登录**——私信是纯私有数据。对比 `/api/tags` 对游客开放，再次说明：**认证不是"整个模块一刀切"，而是逐个端点判断数据是否私有。**

### ⚠️ 路由声明顺序：一个会静默出错的坑

`main.py` 里这五个端点的**实际排列顺序**：

```python
@app.post("/api/messages")                  # ①
@app.get("/api/messages")                   # ②
@app.get("/api/messages/unread-count")      # ③ ← 字面量路径
@app.get("/api/messages/{username}")        # ④ ← 路径参数
@app.put("/api/messages/{username}/read")   # ⑤
```

③ 必须在 ④ **之前**，这不是风格偏好，而是**功能正确性的前提**。原因：**FastAPI（底层是 Starlette）按注册顺序自上而下匹配路由，第一个匹配上的就赢。**

```
如果顺序反了（④ 在 ③ 前面）：
GET /api/messages/unread-count
   → ④ 的 /api/messages/{username} 能匹配任意字符串，"unread-count" 就是一个合法 username
   → 交给 get_messages_with_user(db, me, "unread-count") → 没有这个用户 → None
   → 404 "用户不存在"
结果：角标请求永远 404、未读私信数永远显示不出来，而后端不报任何错、
      日志里只有一条正常的 404 —— 极难排查。
```

这类问题叫"**字面量路径与路径参数冲突**"，是所有 Web 框架的通用陷阱（Flask、Express、Django 都有类似行为）。有三种规避法：**字面量路径写在前面**（本项目做法，约定 `/messages/unread-count` 这类固定路径全部排在 `/messages/{username}` 之前）；给参数加约束（例如把 `username` 声明成有正则限制的类型，让 `unread-count` 匹配不上）；换一个不冲突的路径（例如 `/api/messages/me/unread-count`，从结构上杜绝歧义）。

项目顺序虽然是对的，但**代码里没有任何注释说明"这个顺序不能动"**。将来有人整理代码块、按字母排序，很容易把 ③ 挪到 ④ 后面，然后收获一个"角标偶尔不显示"的诡异 bug。稳妥做法是加一行注释：

```python
# ⚠️ unread-count 必须声明在 /{username} 之前，否则会被当作用户名匹配掉
@app.get("/api/messages/unread-count")
def unread_message_count(...):
```

> 通知模块恰好安全：`/api/notifications/unread-count` 虽然也是字面量，但它会竞争的 `{notif_id}/read` 是**两段**路径，结构不同不会冲突。**这就是这类 bug 麻烦的地方：它是否发生，取决于另一个路由长什么样。**

## 7. 前端 `MessagesView.vue`：归一化，一个列表吃两种数据

后端给的是两种形状完全不同的数据，前端只有一个列表要渲染，中间的桥就是**归一化**：

```javascript
// 同时获取通知和私信
const [notifRes, convRes] = await Promise.all([
  getNotifications(1, 50),
  getConversations(),
]);

const notifications = (notifRes.data.items || []).map(n => ({
  type: "notification", id: `notif-${n.id}`, sourceId: n.id,
  username: "系统通知", avatar: "",
  preview: n.type === "reply" ? "有人回复了你的帖子" : "你有新通知",
  time: n.created_at, unread: !n.is_read, topicId: n.topic_id,
}));

const conversations = (convRes.data || []).map(c => ({
  type: "message", id: `msg-${c.username}`,
  username: c.username, avatar: c.avatar, preview: c.last_message,
  time: c.last_message_at, unread: c.unread_count > 0, unreadCount: c.unread_count,
}));

// 合并并按时间倒序
messages.value = [...notifications, ...conversations]
  .sort((a, b) => new Date(b.time) - new Date(a.time));
```

**`Promise.all` 而不是两个 `await` 串行**：两个请求互不依赖，串行总耗时 = `t1 + t2`，并发 ≈ `max(t1, t2)`。代价是**错误处理变粗**——任何一个失败整体就 reject、显示"加载失败"；这个取舍对收件箱合适：两个数据要一起展示，缺一个列表就是残的。

要理解归一化的意义，对比两种数据的原始字段就够了：**谁**——通知没有（硬编码"系统通知"）vs 私信的 `username`；**摘要**——通知没有、要按 `type` 现生成 vs 私信的 `last_message`；**时间**——`created_at` vs `last_message_at`；**未读**——`is_read`（布尔取反）vs `unread_count`（数字 `> 0`）。

不归一化的话，模板里到处都会是 `msg.type === 'notification' ? n.created_at : c.last_message_at` 这种三元。归一化把"数据源差异"全部收拢到 `map` 这一步，渲染层只认一种结构；将来再加一种来源（@ 提及、系统公告），只需再写一个 `map`，渲染层一行都不用改。

几个细节：**① `type` 是归一化的"原籍标记"**——保留它才能继续做点击分流，**统一的是"怎么显示"，保留的是"点了做什么"**；**② `sort` 必须用 `new Date(b.time) - new Date(a.time)`**——时间在这里是 ISO 字符串，`b.time - a.time` 得到 `NaN`，排序会静默失效、**列表看起来"没排序"但又不报错**，是最难发现的一类 bug。另外 `id` 加前缀（`notif-`/`msg-`）防两类 id 撞车，`sourceId` 则保留通知的**原始 id**（`id` 已被加了前缀，不能直接拿去调接口）。

### 渲染与点击分派

模板里靠 `type` 区分三处：头像、名字样式、角标数字。**通知用品牌符号 `✦`（真实用户不会有这个字符）+ 主色渐变底**，一眼就能分清"系统通知"和"真人消息"。角标 `{{ msg.type === 'message' && msg.unreadCount ? msg.unreadCount : '' }}`：只有私信显示具体数字（未读几条），通知只显示空红点——"系统通知未读 5 条"价值很低，而"bob 给我发了 3 条"值得知道数量。

```javascript
async function openMessage(msg) {
  if (msg.type === "notification") {
    // 标记通知已读
    if (msg.unread) {
      try { await markRead(msg.sourceId); } catch {}
    }
    if (msg.topicId) {
      router.push(`/topic/${msg.topicId}`);
    }
  } else {
    router.push(`/messages/${msg.username}`);
  }
}
```

| 类型 | 先做的事 | 跳转到 |
|------|---------|--------|
| 通知 | 未读则调 `markRead(sourceId)` 标记已读 | `/topic/{topicId}` 相关帖子 |
| 私信 | 什么都不做 | `/messages/{username}` 聊天页 |

**私信不用在这里标记已读**，因为第 5 节那个接口读取对话时会自动标记（"打开即已读"）。同一个产品概念，两种实现路径：通知因为点击后要跳到另一页面、内容在那边才展示，所以"点击时标记"更准确；私信"读取即标记"更简洁。`try { ... } catch {}` 的空 catch 是有意的：**标记已读失败不该阻止用户查看通知内容**——它是"尽力而为"的副作用，不是跳转的前提。

## 8. 前端 `ChatView.vue`：气泡、轮询与输入法

```html
<div v-for="msg in messages" :key="msg.id"
     class="message" :class="{ mine: msg.sender_id === auth.user?.id }">
  <div class="bubble">{{ msg.content }}</div>
  <div class="time">{{ formatTime(msg.created_at) }}</div>
</div>
```

```css
.message.mine { align-self: flex-end; align-items: flex-end; }
.message.mine .bubble { background: var(--color-primary); color: #fff; }
```

`msg.sender_id === auth.user?.id`：**自己发的靠右、主色底白字（`.mine` 类做 `align-self: flex-end` + 主色背景）；对方发的靠左、浅底描边。** 用可选链是必要的——`auth.user` 可能还没从 localStorage 恢复出来，直接写 `auth.user.id` 首次渲染就抛 `TypeError`；用 `?.` 后 `null === undefined` 得到 `false`，**消息先渲染成"对方的"样式，等用户信息加载完再翻转**，这个短暂错位比白屏崩溃好得多。

**发送后重新拉取，而不是本地追加：**

```javascript
async function handleSend() {
  const content = newMessage.value.trim();
  if (!content || sending.value) return;
  sending.value = true;
  try {
    await sendMessage(route.params.username, content);
    newMessage.value = "";
    await fetchMessages();
  } catch (e) {
    showToast.error(e.response?.data?.detail || "发送失败");
  } finally {
    sending.value = false;
  }
}
```

本地 `push` 一条"临时消息"不用额外请求、响应"瞬间"，但要自己编造 id 和时间、顺序可能与服务端不一致；重新拉取则数据 100% 与后端一致，代价只是多一次请求。对聊天这种低频操作，这个取舍划算——**"服务端是唯一真相来源，客户端不猜"**。`if (!content || sending.value) return` 是防重复提交（按钮也 `:disabled`，双保险）；**前端防重是体验，后端防重才是安全**，但私信接口不做幂等，因为"连发两条一样的话"在聊天里完全正常。

**每 10 秒轮询 + 卸载清理：**

```javascript
let pollTimer = null;

onMounted(() => {
  fetchMessages();
  // 每 10 秒轮询新消息
  pollTimer = setInterval(fetchMessages, 10000);
});

onUnmounted(() => {
  if (pollTimer) clearInterval(pollTimer);
});
```

项目里有两个**节奏不同**的定时器：`App.vue` 30 秒拉角标未读数（角标延迟半分钟没人介意，且它**全局常驻**、必须克制）；`ChatView` 10 秒拉当前对话（正在聊天时，10 秒内看到对方回复可以接受，再快就浪费）。`onUnmounted` 里清定时器是**必须的**：不清的话每进出一个对话就留下一个还在跑的 timer，越逛每 10 秒发出的重复请求越多，还查不出原因。**通用规则：`onMounted` 里开的 `setInterval`/事件监听/WebSocket，`onUnmounted` 里必须关。**

**Enter 发送与中文输入法：**

```javascript
function onKeydown(e) {
  if (e.key === "Enter" && !e.shiftKey && !e.isComposing) {
    e.preventDefault();
    handleSend();
  }
}
```

三个条件缺一不可：`e.key === "Enter"` 只处理回车；`!e.shiftKey` 把 Shift+Enter 留给"换行"（用的是 `<textarea>`，不特判的话回车就被"发送"独占，用户发不了多行）；`e.preventDefault()` 阻止回车在 textarea 里插入换行符。第三个 `!e.isComposing` 是**中文/日文/韩文用户的专属坑**，很多教程会漏掉：

```
用拼音打字分两个阶段：
第 1 阶段（组字）敲 "nihao" → 输入框里是带下划线的拼音、弹出候选词面板
     ← 此时用户按【回车】确认候选词把"你好"上屏，这个回车同样触发 keydown！
第 2 阶段（上屏完成）
```

只判断 `Enter && !shiftKey` 的话，用户用拼音选词时**每按一次回车就会把还没写完的半句话发出去**——中文用户一用就炸，而英文开发者往往永远测不出来。`e.isComposing` 在组字期间为 `true`、上屏后变回 `false`，加上它，组字期间的回车就只用于选词。这和"用 `new Date` 比较时间"属于同一类：**都是"不写不报错、写了才知道为什么必要"的实战经验。**

**同组件复用：从一个对话切到另一个：**

```javascript
// 路由参数变化时重新加载（同组件复用场景）
watch(() => route.params.username, (newName) => {
  if (newName) {
    loading.value = true;
    error.value = "";
    fetchMessages();
  }
});
```

`/messages/bob` 和 `/messages/carol` 指向**同一个组件**。路由切换时 Vue Router 默认**复用组件实例**、只更新 `route.params`，`onMounted` 不会再执行一次。不写这个 `watch` 的话，用户在 bob 的聊天页点开 carol，看到的**还是 bob 的聊天记录**，只有顶部标题变了。**通用规则：只要组件的数据来源里有 `route.params`/`route.query`，就必须 `watch` 它**（`TopicDetailView`、`UserProfile`、`TopicEditView`、`HomeView` 都遵守）。`watch` 里重置 `loading`、清空 `error` 也是必要的：否则 bob 页面报过错的话，进 carol 会先闪一下"用户不存在"。

## 9. 角标与入口：把私信接进全局

`App.vue` 把两个未读数加起来：`const totalUnread = computed(() => unreadCount.value + unreadMessageCount.value)`，于是"未读通知 3 + 未读私信 2"就显示成 5。

**为什么相加？** 因为统一收件箱在同一页面展示两类数据，角标是"这个入口里有多少东西没看"。**只算通知，用户就会漏掉私信；只算私信，就会漏掉回复。** 这是"合并入口"这个决策必然带来的连带改动（`totalUnread > 99 ? '99+' : totalUnread` 防止三位数撑破角标）。

数据来自两个**独立**接口（`/notifications/unread-count`、`/messages/unread-count`），由两个函数分别拉取、各自更新不同的 `ref`，任一失败不影响另一个——所以这里**没有用 `Promise.all`**：它适合"要一起成功"，这里适合"各自独立"。两个 `catch {}` 都是空的且是**故意的**：角标拉取失败（未登录、网络抖动）不该产生任何用户可见的错误——**它不是页面内容，失败就静默保留上一次的值**。

另一个入口是用户主页的"发私信"按钮，`v-if="auth.user && auth.user.username !== profile.username"`——未登录不显示、**看自己的主页也不显示**（你没法给自己发私信，后端也会返回 400）。**"前端藏起来"和"后端拒绝"是两件事，都要做**：前端 `v-if` 是体验优化，后端 `receiver.id == sender_id → 400` 是安全底线。**永远不要用前端的隐藏来代替后端的校验。**

## 本章要点

- 通知与私信在 `6ae6ea4`（05-31）合并为统一收件箱；`/notifications` 现在 `redirect` 到 `/messages`，`NotificationsView.vue` 已是**无路由、无引用的死代码**
- `Message` 表有**两个外键指向 `users`**，两个 `relationship` 必须显式写 `foreign_keys=[sender_id]` / `foreign_keys=[receiver_id]`，否则抛 `AmbiguousForeignKeysError`——SQLAlchemy 拒绝猜，这是好事
- 两个复合索引各有分工：`(sender_id, receiver_id)` 服务双向对话查询，`(receiver_id, is_read)` 服务未读统计；**等值列在前、高区分度列在左**
- `send_message` 失败返回 `None`（收件人不存在或发给自己），由路由层翻译成 400；数据层不认识 HTTP
- `get_conversations` 是本章最难的一段，因为**没有会话表**，会话要从消息推算：
  - 子查询一用 `case()` 算出"对方是谁"（我发的取 `receiver_id`，否则取 `sender_id`），再 `group_by` + `max(id)` 拿每个会话的最新消息
  - 子查询二按 `sender_id` 分组数未读
  - 主查询 `join users`（换成人名）/ `join messages`（取最新内容）/ **`outerjoin` 未读数** + `coalesce(cnt, 0)`
- **没有未读的会话必须靠 `outerjoin` 才能保留**——和第十八章 `get_all_tags` 是同一个理由
- `get_messages_with_user` 用 `or_((我→TA) & ..., (TA→我) & ...)` 组双向条件；SQLAlchemy 里拼条件用 `&`/`|`/`~` 且**括号不能省**，不能用 Python 的 `and`/`or`
- `GET /api/messages/{username}` **读取后自动标记已读**（先取数据再标记）；前端因此不需要额外请求
- **`/api/messages/unread-count` 必须声明在 `/api/messages/{username}` 之前**：FastAPI 按注册顺序匹配，反了的话 `unread-count` 会被当成用户名匹配掉并返回 404，且不报任何错——这是"字面量路径 + 路径参数"共存的通用陷阱
- `MessagesView` 用 `Promise.all` 并发拉两种数据，**归一化**成统一结构（`type` 字段保留原籍用于点击分流，`id` 加前缀防撞车）；排序必须 `new Date(b.time) - new Date(a.time)`，ISO 字符串直接相减会得到 `NaN` 让排序静默失效
- `ChatView` 发送后**重新拉取**而不是本地追加（服务端是唯一真相）；每 10 秒轮询、`onUnmounted` 清 timer；导航栏角标 30 秒轮询且**通知数 + 私信数相加**
- Enter 发送必须判断 **`!e.isComposing`**，否则中文输入法选词时按回车会误发消息
- 靠 `route.params` 取数据的组件必须 `watch` 路由参数，否则同组件复用时数据不会刷新
- 前端 `v-if` 隐藏按钮只是体验，**后端的 400 才是安全边界**，两者都要有
