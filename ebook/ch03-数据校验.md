# 第三章：数据校验 — schemas.py

## models.py vs schemas.py

| | models.py | schemas.py |
|---|---|---|
| 用途 | 和数据库打交道 | 和 API 请求/响应打交道 |
| 基类 | `DeclarativeBase` | `BaseModel` |
| 校验方式 | 数据库约束（NOT NULL, UNIQUE） | Pydantic 类型检查 + field_validator |
| 序列化 | 需手动处理 | 自动 `.model_dump()` |

models 定义数据**怎么存**，schemas 定义数据**怎么传**。两者一一对应但绝不混用——这是这一章最重要的一句话。

## 请求模型（客户端 → 服务器）

```python
class UserRegister(BaseModel):
    username: str
    password: str

class UserLogin(BaseModel):
    username: str
    password: str

class PasswordChange(BaseModel):
    old_password: str
    new_password: str

class TopicCreate(BaseModel):
    title: str
    content: str = ""
    tags: list[str] = []

class TopicUpdate(BaseModel):
    title: str | None = None
    content: str | None = None
    tags: list[str] | None = None

class CommentCreate(BaseModel):
    content: str
    topic_id: int
    parent_id: int | None = None

class MessageCreate(BaseModel):
    receiver: str = Field(min_length=1, max_length=20)
    content: str = Field(min_length=1, max_length=5000)
```

Pydantic 自动类型校验。客户端传 `{"title": 123}`（数字而非字符串）→ FastAPI 自动返回 **422 错误**。

几个设计细节值得留意：

- **`TopicCreate.tags: list[str] = []`** — 标签是可选的字符串列表，不传就是空列表。前端传的是标签名（如 `["Python", "FastAPI"]`），后端再负责规范化和查重
- **`TopicUpdate` 所有字段可为 None** — "改什么传什么"。路由层用 `data.model_dump(exclude_unset=True)` 只取出客户端真正传了的字段，没传的字段保持原值
- **`MessageCreate.receiver` 长度限制 1~20** — 用 `Field(...)` 约束。`receiver` 传的是**对方用户名**而不是 id，接口层对用户更友好

> ⚠️ 当前代码的一个真实疏漏：`schemas.py` 顶部写的是 `from pydantic import BaseModel, field_validator`，**并没有导入 `Field`**。上面 `MessageCreate` 里用到的 `Field` 在运行时会是 `NameError`。正确写法是把导入行补成 `from pydantic import BaseModel, Field, field_validator`。这里保留原样展示，是为了让你在阅读源码时能对上号——遇到 `NameError: name 'Field' is not defined` 时知道该改哪里。（本教程只讲文档，不修改源码。）

## 响应模型（服务器 → 客户端）

```python
class UserResponse(BaseModel):
    id: int
    username: str
    avatar: str
    bio: str
    github_url: str
    is_admin: bool
    topic_count: int = 0
    comment_count: int = 0
    created_at: datetime

    model_config = {"from_attributes": True}
```

### `from_attributes` 配置

告诉 Pydantic：可以从 SQLAlchemy ORM 对象的属性读取值来填充这个模型。没有这行，就不能直接把数据库查出的 User 对象转成 API 响应。

**安全细节**：User 表有 `password_hash` 字段，但 `UserResponse` 没有定义 → 返回给客户端时自动过滤，密码不会泄露。

### 带自定义校验的更新模型

`UserUpdate` 是所有字段可选的"改什么传什么"模型，但它多了一个自定义校验：

```python
class UserUpdate(BaseModel):
    avatar: str | None = None
    bio: str | None = None
    github_url: str | None = None

    @field_validator("github_url")
    @classmethod
    def validate_github_url(cls, v):
        if v and not v.startswith(("https://", "http://")):
            raise ValueError("必须是有效的 URL")
        return v
```

`@field_validator` 在默认类型校验之后运行，用来加业务规则。这里要求 `github_url` 必须以 `http://` 或 `https://` 开头，否则抛出 `ValueError`——Pydantic 会把它汇总成 422 响应。注意 `if v` 的判断：允许传空字符串（表示清空该字段）。

## 递归模型 — 评论树

```python
class CommentResponse(BaseModel):
    id: int
    content: str
    topic_id: int
    user_id: int
    username: str
    parent_id: int | None = None
    created_at: datetime
    replies: list["CommentResponse"] = []    # 自己引用自己

    model_config = {"from_attributes": True}

    @field_validator("username", mode="before")
    @classmethod
    def extract_username(cls, v):
        return getattr(v, "username", v)
```

### field_validator 详解

Comment 数据库对象没有直接的 `username` 字段，用户名在关联的 User 对象里（`comment.author.username`）。Comment 模型定义了一个 `@property`：

```python
@property
def username(self):
    return self.author.username if self.author else ""
```

`field_validator("username", mode="before")` 在 Pydantic 解析之前拦截，此时 `v` 还是 SQLAlchemy 对象，`getattr(v, "username", v)` 触发 `@property` 拿到用户名。

`mode="before"` 是关键：默认的校验器在类型转换**之后**运行，那时 `v` 已经被当成字符串处理、报错退出；`before` 让它在类型转换**之前**先动手。要记住的道理是——**两层模型之间需要"翻译层"，`@property` + `field_validator` 就是最干净的那种**。

## 嵌套响应 — 帖子详情

```python
class AuthorInfo(BaseModel):
    id: int
    username: str
    avatar: str
    model_config = {"from_attributes": True}

class TagResponse(BaseModel):
    id: int
    name: str
    slug: str
    model_config = {"from_attributes": True}

class TopicDetailResponse(BaseModel):
    id: int
    title: str
    content: str
    author: AuthorInfo | None = None       # 嵌套作者信息
    view_count: int = 0
    created_at: datetime
    updated_at: datetime
    likes_count: int = 0
    is_liked: bool = False                # 当前登录用户是否已点赞
    comments: list[CommentResponse] = []   # 嵌套评论树（递归）
    tags: list[TagResponse] = []          # 嵌套标签
    is_pinned: bool = False
    is_featured: bool = False

    model_config = {"from_attributes": True}
```

嵌套结构：

```
TopicDetailResponse
  ├── author: AuthorInfo          ← 只返回基本资料（不含密码等敏感字段）
  ├── tags: TagResponse[]         ← 标签列表
  └── comments: CommentResponse[] ← 评论列表（递归嵌套 replies）
```

`is_liked` 是个"因人而异"的字段：同一篇帖子，已登录用户看到 `true`、游客看到 `false`。它不存在于数据库里，而是路由层根据当前用户即时算出来填进去的（详见第六章）。

## 列表响应

```python
class TopicListResponse(BaseModel):
    id: int
    title: str
    author: AuthorInfo | None = None
    view_count: int = 0
    comment_count: int = 0
    likes_count: int = 0
    last_comment_at: datetime | None = None
    created_at: datetime
    tags: list[TagResponse] = []
    is_pinned: bool = False
    is_featured: bool = False

    model_config = {"from_attributes": True}
```

列表视图不需要返回帖子的全文内容，只需要标题、作者、统计信息、标签和置顶/加精标记就够了。注意 `TopicListResponse` **没有** `content` 字段——这是刻意的：列表页返回 20 篇帖子的全文会造成大量无谓传输。

## 用户主页与通知/私信的响应模型

```python
class UserProfileResponse(BaseModel):
    id: int
    username: str
    avatar: str
    bio: str
    github_url: str
    topic_count: int = 0
    comment_count: int = 0
    created_at: datetime
    topics: list[TopicListResponse] = []    # 主页里嵌这个用户发的帖子

    model_config = {"from_attributes": True}

class NotificationResponse(BaseModel):
    id: int
    type: str
    topic_id: int | None = None
    comment_id: int | None = None
    is_read: bool
    created_at: datetime

    model_config = {"from_attributes": True}
```

私信则是"收发双方 + 会话列表"三个模型：

```python
class MessageResponse(BaseModel):
    id: int
    sender_id: int
    receiver_id: int
    content: str
    is_read: bool
    created_at: datetime
    model_config = {"from_attributes": True}

class ConversationResponse(BaseModel):
    username: str
    avatar: str
    last_message: str
    last_message_at: datetime
    unread_count: int
```

`ConversationResponse` 有一个特点：**它不是任何一张表**。它是 `crud.get_conversations` 用两个子查询拼出来的聚合结果（"对方是谁 + 最后一条消息 + 未读数"），所以字段是"对方用户名"而不是"用户 id"。这说明 schemas 不只是 ORM 的影子，也可以描述纯粹的计算结果。

## Schema 设计模式总结

| 模式 | 示例 | 说明 |
|------|------|------|
| 创建请求 | `TopicCreate` / `MessageCreate` | 只包含用户需填的字段，不含 id 等自动生成字段 |
| 更新请求 | `UserUpdate` / `TopicUpdate` | 所有字段可选（`str \| None = None`），改什么传什么 |
| 响应模型 | `UserResponse` | 包含所有输出字段，自动过滤敏感信息 |
| 列表响应 | `TopicListResponse` | 只含列表展示需要的字段（无正文） |
| 详情响应 | `TopicDetailResponse` | 含完整信息 + 嵌套关联对象 |
| 聚合响应 | `ConversationResponse` | 不对应表，描述多表拼接出的计算结果 |

## 本章要点

- Pydantic 负责 API 的数据校验和序列化
- `from_attributes` 连接 ORM 和 Pydantic 的桥梁
- `field_validator` 在字段赋值前后做自定义处理（`mode="before"` 先于类型转换）
- 递归 `list["CommentResponse"]` 实现无限嵌套
- 响应模型自动过滤敏感字段，安全由类型系统保障
- 请求模型负责"收什么"，响应模型负责"给什么"，两者严格分开
- `ConversationResponse` 说明 schema 也能描述非数据库产出的聚合数据
