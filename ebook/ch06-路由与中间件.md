# 第六章：路由与中间件 — main.py

main.py 是整个后端的**大脑**——串联所有模块，处理每一个 HTTP 请求。全文 475 行，定义了 **29 个 `/api` 端点**（外加一个返回服务标识的 `GET /`）。

## 启动生命周期

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    os.makedirs(AVATAR_DIR, exist_ok=True)
    ensure_schema()
    yield


app = FastAPI(title="Forum API", lifespan=lifespan)
app.state.limiter = limiter
```

`lifespan` 是 FastAPI 的"启动/关闭钩子"。这里在服务真正开始接受请求**之前**做两件事：

1. **`os.makedirs(AVATAR_DIR, exist_ok=True)`** — 确保头像上传目录存在。`exist_ok=True` 让"目录已存在"不报错，所以这行可以反复执行
2. **`ensure_schema()`** — 建表 + 补列（见第二章）

顺序不能反：先有目录，再检查表。`yield` 之后的分号位置是"服务关闭时"要执行的代码，这里没有额外清理动作。

`app.state.limiter = limiter` 是 slowapi 的要求——把限流器挂到应用状态上，装饰器 `@limiter.limit(...)` 才能找到它。

## 中间件

中间件像过滤管道——每个请求和响应都会经过它们。

### CORS 中间件

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=[os.environ.get("CORS_ORIGIN", "http://localhost:5173")],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**CORS 是什么？** 浏览器同源策略：A 网站的 JS 不能访问 B 网站的数据。前端在 `localhost:5173`，后端在 `localhost:8000`，端口不同 → 不同源 → 浏览器拦截。CORS 中间件在响应头加 `Access-Control-Allow-Origin` 来放行。

允许的来源从环境变量 `CORS_ORIGIN` 读取，默认是本地开发地址。生产环境部署时把它设成真实域名即可，不用改代码（第九章会看到 docker-compose 里就是这么传的）。

### 请求日志

```python
@app.middleware("http")
async def log_requests(request: Request, call_next):
    start = time.time()
    response = await call_next(request)
    duration = time.time() - start
    logger.info(f"{request.method} {request.url.path} {response.status_code} ({duration:.3f}s)")
    return response
```

记录示例：`GET /api/topics 200 (0.032s)`

这是"自定义中间件"的写法：用 `@app.middleware("http")` 装饰一个 `async` 函数，`call_next(request)` 就是"把请求交给后面的处理链"。因为它在 `call_next` 前后都插了代码，所以能算耗时。

`duration:.3f` 保留三位小数，能看出慢请求——排查性能问题时，日志里的耗时往往是最先暴露问题的线索。

## 统一错误处理

```python
@app.exception_handler(404)
async def not_found_handler(request: Request, exc):
    return JSONResponse(status_code=404, content={"detail": "Not found"})

@app.exception_handler(500)
async def server_error_handler(request: Request, exc):
    logger.error(f"500 on {request.method} {request.url.path}: {exc}\n{traceback.format_exc()}")
    return JSONResponse(status_code=500, content={"detail": "Internal server error"})

@app.exception_handler(RateLimitExceeded)
async def rate_limit_handler(request: Request, exc):
    return JSONResponse(status_code=429, content={"detail": "Too many requests"})

@app.exception_handler(Exception)
async def unhandled_exception_handler(request: Request, exc: Exception):
    logger.error(f"Unhandled error on {request.method} {request.url.path}: {exc}\n{traceback.format_exc()}")
    return JSONResponse(status_code=500, content={"detail": "Internal server error"})
```

一共四个处理器，各自对应一类"漏网之鱼"：

- **404** — 路径不存在
- **500** — 服务端错误
- **429** — 触发限流（`RateLimitExceeded` 是 slowapi 的异常）
- **`Exception` 兜底** — 任何没被上面捕获的异常。它确保**客户端收到的永远是 `{"detail": "..."}` 格式**，而不是一坨 HTML 堆栈

两个 500 相关的处理器都用 `logger.error(...)` 把完整的 `traceback.format_exc()` 写进日志。这是"对外简洁、对内详尽"的安全习惯：错误细节只留在服务端日志里，绝不返回给客户端，否则可能泄露文件路径、SQL 结构等信息。

## HTML 过滤（防 XSS）

```python
ALLOWED_TAGS = ["b", "i", "em", "strong", "a", "p", "br", "ul", "ol", "li",
                "pre", "code", "h1", "h2", "h3", "h4", "h5", "h6",
                "blockquote", "img", "table", "thead", "tbody", "tr", "th", "td", "hr"]
ALLOWED_ATTRS = {"a": ["href", "title"], "img": ["src", "alt"], "code": ["class"]}


def sanitize(text: str) -> str:
    return bleach.clean(text, tags=ALLOWED_TAGS, attributes=ALLOWED_ATTRS,
                        protocols=["http", "https", "mailto"], strip=True)
```

用户输入可能包含 `<script>alert('xss')</script>`，bleach 只保留白名单中的安全标签。

这份白名单值得逐项体会：

- **保留了 Markdown 的产物标签**：`h1~h6`、`pre`、`code`、`blockquote`、`table` 系列、`hr`、`img`。因为帖子正文是前端 Markdown 渲染后**把 HTML 字符串发回后端**保存的，如果白名单太窄，代码块、表格、标题这些正常排版会被剥掉
- **属性白名单限定到标签**：只放行 `a[href,title]`、`img[src,alt]`、`code[class]`。也就是说 `<img src="...">` 允许，但 `<img onerror="...">` 里的 `onerror` 会被删掉——这是 XSS 最常见的入口之一
- **`protocols=["http", "https", "mailto"]`** — 防止 `javascript:` 伪协议链接（`<a href="javascript:alert(1)">` 是另一个经典入口）
- **`strip=True`** — 遇到不在白名单里的标签时**剥掉标签但保留文字内容**，而不是整段丢弃

`sanitize` 被用在所有用户产出文本的地方：发帖、改帖、评论、私信。

## 权限检查

```python
def _author_or_admin(topic: Topic, user: User):
    if topic.author_id != user.id and not user.is_admin:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Not your topic")

def _comment_author_or_admin(comment: Comment, user: User):
    if comment.user_id != user.id and not user.is_admin:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Not your comment")
```

两个 helper 封装了同一条规则："**本人或管理员**才能操作"。帖子相关路由用 `_author_or_admin`，评论相关用 `_comment_author_or_admin`。它们**不是 FastAPI 依赖**（没写 `Depends`），而是普通函数，被路由函数显式调用——因为要先拿到数据库里的 topic/comment 对象才能判断归属。

注意这里只处理"存在但无权限"→ 403；"根本不存在"→ 404 由调用方负责，两者分开，前端才能区分"帖子没了"和"这不是你的帖子"。

## 限流配置

```python
limiter = Limiter(key_func=get_remote_address)
```

`get_remote_address` 表示按**请求来源 IP** 计数。各接口的限流强度如下：

| 限流 | 接口 | 为什么这么定 |
|------|------|------|
| **5/min** | `POST /api/auth/register`、`PUT /api/auth/password` | 注册和改密码最敏感，严格限制防刷 |
| **10/min** | `POST /api/auth/login` | 登录尝试防暴力破解 |
| **10/min** | 发帖 / 改帖 / 删帖 / 评论 / 私信 / 上传头像 | 写操作统一 10/min，防灌水 |
| 不限 | 读操作（列表、详情、通知、私信列表等） | 读接口放开，保证正常浏览体验 |

被限流时，slowapi 抛出 `RateLimitExceeded`，由上面那个 429 处理器转成 `{"detail": "Too many requests"}`。

被 `@limiter.limit(...)` 装饰的函数**第一个参数必须是 `request: Request`**（即使函数体用不到），因为 slowapi 要靠它拿到客户端标识。

## 路由详解

### 认证路由

```python
@app.post("/api/auth/register", response_model=UserResponse, status_code=201)
@limiter.limit("5/minute")
def register(request: Request, data: UserRegister, db: Session = Depends(get_db)):
    if get_user_by_username(db, data.username):
        raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail="Username already exists")
    return create_user(db, data.username, data.password)

@app.post("/api/auth/login", response_model=TokenResponse)
@limiter.limit("10/minute")
def login(request: Request, data: UserLogin, db: Session = Depends(get_db)):
    user = get_user_by_username(db, data.username)
    if not user or not verify_password(data.password, user.password_hash):
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Invalid credentials")
    token = create_access_token({"sub": str(user.id)})
    return TokenResponse(access_token=token)
```

- **装饰器顺序**：`@app.post` 在最上，`@limiter.limit` 紧贴函数。顺序写反会导致限流不生效
- **`status_code=201`** — 注册是"创建资源"，语义上应该返回 201 Created 而不是 200
- **`response_model=UserResponse`** — 返回的 User 对象会被按 schema 过滤，`password_hash` 不会泄露
- `if not user or not verify_password(...)` — 无论是"用户不存在"还是"密码错误"，都返回同样的 401，防止攻击者试探用户名
- **`{"sub": str(user.id)}`** — token 里只放用户 id，不放用户名或权限，越少越安全

改密码路由单独限流 5/min，并且先验证原密码：

```python
@app.put("/api/auth/password")
@limiter.limit("5/minute")
def update_password(request: Request, data: PasswordChange, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    if not verify_password(data.old_password, current_user.password_hash):
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="原密码错误")
    change_password(db, current_user, data.new_password)
    return {"message": "密码已更新"}
```

### 帖子路由

```python
# 列表（公开）
@app.get("/api/topics")
def list_topics(
    page: int = Query(1, ge=1),
    size: int = Query(10, ge=1, le=100),
    q: str = "",
    tag: str = "",
    db: Session = Depends(get_db),
):
    items, total = get_topics(db, page=page, size=size, q=q, tag=tag)
    return {
        "items": items,
        "total": total,
        "page": page,
        "size": size,
        "pages": (total + size - 1) // size if total > 0 else 0,
    }
```

- **`Query(1, ge=1)`** — 用 `Query` 给参数加约束：`page` 最小 1、`size` 在 1~100 之间。客户端传 `size=99999` 会被 FastAPI 拦下返回 422，避免有人一次拉走整张表
- **`(total + size - 1) // size`** — 向上取整算总页数。`total=10, size=10` 时结果是 1（而不是 `10 // 10 + 1 = 2`）。后面的 `if total > 0 else 0` 是一道防御性写法：`total=0` 时公式本身也会得到 0，这个判断只是把"零结果就是零页"显式表达出来
- 返回的是字典而不是 `response_model`——列表项的字段由 crud 层拼好，直接用即可

```python
# 详情（公开 + 可选登录）
@app.get("/api/topics/{topic_id}", response_model=TopicDetailResponse)
def detail_topic(topic_id: int, db: Session = Depends(get_db), current_user: User | None = Depends(get_optional_user)):
    topic = get_topic_by_id(db, topic_id)
    if not topic:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Topic not found")
    increment_view_count(db, topic)   # +1 浏览量
    is_liked = any(u.id == current_user.id for u in topic.likes) if current_user else False
    return {
        "id": topic.id,
        "title": topic.title,
        "content": topic.content,
        "author": {"id": topic.author.id, "username": topic.author.username, "avatar": topic.author.avatar} if topic.author else None,
        "view_count": topic.view_count,
        "created_at": topic.created_at,
        "updated_at": topic.updated_at,
        "likes_count": len(topic.likes),
        "is_liked": is_liked,
        "comments": build_comment_tree(topic.comments),
        "tags": [{"id": tag.id, "name": tag.name, "slug": tag.slug} for tag in topic.tags],
        "is_pinned": topic.is_pinned,
        "is_featured": topic.is_featured,
    }
```

详情路由把散落在各处的数据"组装"成响应：

- `increment_view_count` 顺手给浏览量 +1——注意放在"确认帖子存在"之后，避免给不存在的 id 也加浏览
- `is_liked` 用 `get_optional_user` 拿到的当前用户，在内存里对 `topic.likes` 做一次 `any(...)` 判断
- `comments` 交给 crud 的 `build_comment_tree` 拼成树
- 返回里手写了 `author`、`tags` 的字段，而不是直接返回 ORM 对象——因为要控制输出形状（比如 tags 里不要多余字段）

**发布与编辑**走"先 sanitize 再入库"：

```python
@app.post("/api/topics", response_model=TopicDetailResponse, status_code=201)
@limiter.limit("10/minute")
def create_topic_route(request: Request, data: TopicCreate, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    return create_topic(db, current_user.id, sanitize(data.title), sanitize(data.content), data.tags)

@app.put("/api/topics/{topic_id}", response_model=TopicDetailResponse)
@limiter.limit("10/minute")
def update_topic_route(request: Request, topic_id: int, data: TopicUpdate, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    topic = get_topic_for_edit(db, topic_id)
    if not topic:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Topic not found")
    _author_or_admin(topic, current_user)
    payload = data.model_dump(exclude_unset=True)
    if payload.get("title"):
        payload["title"] = sanitize(payload["title"])
    if payload.get("content"):
        payload["content"] = sanitize(payload["content"])
    return update_topic(db, topic, payload)
```

### 权限检查三部曲

```python
@app.delete("/api/topics/{topic_id}", status_code=204)
@limiter.limit("10/minute")
def delete_topic_route(request: Request, topic_id: int, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    topic = get_topic_for_edit(db, topic_id)   # 1. 查数据库
    if not topic:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND)  # 2. 不存在？404
    _author_or_admin(topic, current_user)      # 3. 没权限？403
    delete_topic(db, topic)
```

这个"查 → 判存在 → 判权限"的三部曲在改帖、删帖、编辑回填、点赞、置顶、加精等所有"针对某个具体帖子"的路由上反复出现。删帖成功返回 `status_code=204`（No Content），语义上"成功且没有响应体"。

### 评论路由

```python
@app.post("/api/comments", response_model=CommentResponse, status_code=201)
@limiter.limit("10/minute")
def create_comment_route(request: Request, data: CommentCreate, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    if not get_topic_for_edit(db, data.topic_id):
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Topic not found")
    try:
        return create_comment(db, current_user.id, data.topic_id, sanitize(data.content), data.parent_id)
    except ValueError as e:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail=str(e))

@app.delete("/api/comments/{comment_id}", status_code=204)
def delete_comment_route(comment_id: int, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    comment = get_comment_by_id(db, comment_id)
    if not comment:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Comment not found")
    _comment_author_or_admin(comment, current_user)
    delete_comment(db, comment)
```

创建评论时，crud 层遇到"父评论不存在"会 `raise ValueError`，路由层用 `except ValueError` 接住并转成 400。这是**分层协作**的典型：crud 只表达"业务上的失败"，路由负责翻译成 HTTP 状态码。

```python
@app.get("/api/messages")
def list_conversations(current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    return get_conversations(db, current_user.id)

@app.get("/api/messages/unread-count")
def unread_message_count(current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    return {"count": get_unread_message_count(db, current_user.id)}

@app.get("/api/messages/{username}")
def get_messages_route(username: str, page: int = Query(1, ge=1), size: int = Query(50, ge=1, le=200),
                       current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    result = get_messages_with_user(db, current_user.id, username, page, size)
    if not result:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="用户不存在")
    mark_messages_read(db, current_user.id, username)   # 打开对话即标记已读
    return result

@app.put("/api/messages/{username}/read")
def mark_read_route(username: str, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    mark_messages_read(db, current_user.id, username)
    return {"message": "ok"}
```

`GET /api/messages/{username}` 在返回聊天记录的同时顺手 `mark_messages_read`——符合"打开对话就等于读了消息"的直觉。

### ⚠️ 路由声明顺序的坑

上面这几条私信路由里，藏着一个**新增同类路由时最容易踩的坑**：

```python
@app.get("/api/messages/unread-count")   # ← 必须写在前面
def unread_message_count(...): ...

@app.get("/api/messages/{username}")     # ← 写在后面
def get_messages_route(username: str, ...): ...
```

FastAPI 匹配路由是**按声明顺序自上而下**的。`{username}` 是一个路径参数，能匹配任意字符串。如果把 `/api/messages/unread-count` 声明在 `/api/messages/{username}` **之后**，那么请求 `GET /api/messages/unread-count` 会先被 `{username}` 这一条匹配掉——`username` 被赋值成字符串 `"unread-count"`，然后进入 `get_messages_route`，查不到这个"用户"就返回 404。

所以规矩是：**静态路径必须排在含路径参数的动态路径之前**。通知模块的 `/api/notifications/unread-count`、`/api/notifications/read-all` 与 `/api/notifications/{notif_id}/read` 之间也是同样的道理（好在它们路径层级不同，暂时没冲突，但写新接口时要有这个意识）。

### 头像上传

```python
@app.post("/api/upload/avatar")
@limiter.limit("10/minute")
async def upload_avatar(
    request: Request,
    file: UploadFile = File(...),
    current_user: User = Depends(get_current_user),
):
    if file.content_type not in ALLOWED_IMAGE_TYPES:
        raise HTTPException(status_code=400, detail="不支持的文件类型，请上传 JPG/PNG/GIF/WebP 图片")

    content = await file.read()
    if len(content) > MAX_AVATAR_SIZE:
        raise HTTPException(status_code=400, detail="文件大小不能超过 2MB")

    # 验证文件魔术字节，防止伪造 content-type
    detected = _detect_image_type(content)
    if detected not in ("jpeg", "png", "gif", "webp"):
        raise HTTPException(status_code=400, detail="文件内容不是有效图片")

    # 扩展名由检测出的真实格式决定，不信任用户文件名
    filename = f"{uuid.uuid4()}{EXT_BY_TYPE[detected]}"
    filepath = os.path.join(AVATAR_DIR, filename)

    with open(filepath, "wb") as f:
        f.write(content)

    return {"url": f"/uploads/avatars/{filename}"}
```

这是全篇**唯一一个 `async` 的接口**，因为文件读取要 `await`。它做了一共五道校验，值得逐个理解为什么要这么做：

1. **必须登录**（`get_current_user`）—— 不能匿名上传，否则会被当成免费图床
2. **限流 10/min** —— 防止有人脚本批量上传占满磁盘
3. **`content_type` 白名单** —— `file.content_type` 是客户端**自己声称**的类型，不可信，但作为第一道"快速失败"的过滤仍有价值
4. **大小限制 2MB** —— `await file.read()` 读出全部内容后判断长度
5. **魔术字节校验（`_detect_image_type`）** —— 前一道 `content_type` 可以被轻松伪造（把木马文件改名成 `.jpg` 再声明 `image/jpeg`）。`_detect_image_type()` 读取文件**开头几个字节**判断真实格式，这才是真正可靠的一道防线。它是 `main.py` 里的一个小函数，手动比对 jpeg（`FF D8 FF`）、png（`89 50 4E 47…`）、gif（`GIF87a/89a`）、webp（`RIFF…WEBP`）四种文件头，不依赖任何第三方库

文件名用 `uuid.uuid4()` 重新生成，**完全不采用用户上传的原始文件名**——既避免了路径穿越（`../`）、也避免了中文/特殊字符文件名导致的编码问题。**扩展名也不取自用户文件名**，而是用 `EXT_BY_TYPE[detected]` 由第 5 步检测出的真实格式映射（`jpeg→.jpg`、`png→.png`、`gif→.gif`、`webp→.webp`）——否则「真实 PNG 内容 + `avatar.html` 文件名」会让 `StaticFiles` 按扩展名返回 `Content-Type: text/html`。

> 📖 历史教训：这一道校验最初是用标准库 `imghdr` 写的，而且写的是 `imghdr.from_buffer(content)`——一个**根本不存在的函数**（`imghdr` 只有 `what()`），所以端点上线后每次调用都 500。更隐蔽的是 `import imghdr` 写在 `upload_avatar` **函数体内部**，服务启动时完全不报错，只有真正有人上传头像时才暴露。雪上加霜的是 `imghdr` 自 Python 3.11 起废弃、3.13 中被移除。2026-09-26 修复时干脆不引新库，直接手动比对文件头——四种图片格式的魔术字节总共十几行代码，比加一个依赖更划算。

## 本章要点

- `lifespan` 在启动时准备上传目录并调用 `ensure_schema()`；顺序是先目录、后建表
- 中间件有两类：CORS（放行跨域）与 `log_requests`（记录方法/路径/状态码/耗时）
- 四个异常处理器覆盖 404 / 500 / 429 / 兜底 `Exception`，保证客户端永远只看到 `{"detail": ...}`
- `sanitize` 用白名单保留 Markdown 产物标签，属性精确到"标签+属性名"，协议限 http/https/mailto
- 限流按敏感度分级：注册/改密码 5/min，写操作 10/min，读操作不限
- 权限 helper（`_author_or_admin` / `_comment_author_or_admin`）只判 403，"不存在"由路由判 404
- **路由顺序**：静态路径（`/api/messages/unread-count`）必须声明在动态路径（`/api/messages/{username}`）之前
- 头像上传五道校验，最后靠 `_detect_image_type()` 手动比对魔术字节识破伪造的 content-type（早期误用不存在的 `imghdr.from_buffer`，2026-09-26 已修）
