# 第二十章：管理功能与文件上传

本章两块东西性质完全不同：**置顶 / 加精**第一次引入"管理员"这个角色，是一道**权限**问题；**头像上传**第一次让用户往服务器上写文件，是一道**安全**问题。第一块的取舍很典型（能用两个字段解决的事，不要建一张表）；第二块则踩过一个**真实的坑**——这个端点的魔术字节校验曾经写成一个不存在的函数，上线后每次调用都 500。第 4 节把它当作完整案例来拆：现象、原因、为何启动时不报错、以及四种修法（这个 bug 已于 2026-09-26 修复，但案例本身值得留着）。

## 1. 置顶与加精：两个布尔字段就够了

最直接的做法就是在 `topics` 表上加两个字段（对应 `backend/models.py`）：

```python
class Topic(Base):
    __tablename__ = "topics"

    # ...（id / title / content / author_id / view_count 等字段见第二章）
    is_pinned = Column(Boolean, default=False)
    is_featured = Column(Boolean, default=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))
    updated_at = Column(
        DateTime,
        default=lambda: datetime.now(timezone.utc),
        onupdate=lambda: datetime.now(timezone.utc),
    )
```

`is_pinned = True` 表示置顶（永远排在列表最前），`is_featured = True` 表示精华（标题前显示金色徽章）。两个字段互相独立，一篇帖子可以同时是置顶和精华。

**为什么不用一张"帖子标记表"？** 初学者容易条件反射地设计 `topic_marks`（`topic_id` + `mark_type` + `marked_by` + `marked_at`），看着"规范"，但对照需求是**过度设计**：标记种类只有两种且稳定（不像标签要开放给用户）、每帖每类恰好一个值（是"每帖一个值"而非一对多）、不需要审计"谁标记的"、**列表页每行都要读这两个标记**。最后一条最关键：字段放在 `topics` 表里，`SELECT * FROM topics` 顺手就带回来了；放独立表则每次列表都要 `left join`。
**原则：一个属性如果满足"候选值少 + 每行最多一个值 + 查询频繁"，就该是主表上的一个列。** 第十八章的 `topic_tags` 之所以必须是独立表，恰恰因为它三条都不满足（值会增长、每帖多个值、只在筛选时需要）——两个设计放一起对比，比单独看任何一个都更说明"表还是字段"该怎么选。

### 加字段之后：老数据库怎么办

**加字段不是改个模型文件就完事的**——模型只影响新建的表，已存在的表不会自动加列。项目没用 Alembic（第八章讲过取舍），而是在 `backend/database.py` 的 `ensure_schema()` 里做**轻量迁移**：

```python
def ensure_schema():
    """Create tables and apply lightweight migrations."""
    # PostgreSQL 15+ 默认撤销了 public schema 的 CREATE 权限，需要显式授权；
    # 云数据库（RDS、Supabase 等）可能不允许 GRANT，失败时只警告不崩溃。
    try:
        with engine.begin() as conn:
            conn.execute(text("GRANT CREATE ON SCHEMA public TO CURRENT_USER"))
    except Exception:
        logging.getLogger("blog").warning("无法在 public schema 上授权 CREATE，跳过")

    Base.metadata.create_all(bind=engine)

    with engine.begin() as conn:
        conn.execute(text(
            "ALTER TABLE comments ADD COLUMN IF NOT EXISTS parent_id INTEGER REFERENCES comments(id)"
        ))
        conn.execute(text(
            "ALTER TABLE topics ADD COLUMN IF NOT EXISTS is_pinned BOOLEAN DEFAULT FALSE"
        ))
        conn.execute(text(
            "ALTER TABLE topics ADD COLUMN IF NOT EXISTS is_featured BOOLEAN DEFAULT FALSE"
        ))
```

三步：`create_all()` 建缺失的表（已存在的不动）；一串 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 给已存在的表补列；**`IF NOT EXISTS` 让这段 SQL 可以反复执行**——第二次启动时列已经在了，它就是空操作、不报错。

**这就是"幂等"思想用在数据库结构上**（和第七章 seed 的"先查后建"、第四章点赞的"唯一约束 + 捕获异常"同源）。`ensure_schema()` 在 `lifespan` 里每次启动都跑一遍，所以必须幂等。**适用边界**：它只能处理"加列"，处理不了改类型、改约束、拆表、数据回填，所以只适合项目早期；变更复杂起来就该上 Alembic。

> 细节：`DEFAULT FALSE` 是必要的。不给默认值的话，老数据里新列是 `NULL`，而模型声明的是 `default=False`——**`NULL` 和 `False` 在 Python 里不是一回事**（`if topic.is_pinned` 结果相同，但 `topic.is_pinned is False` 不成立）。`DEFAULT FALSE` 让老数据也干净。

### toggle：切换语义的好处与代价

```python
def toggle_topic_pin(db: Session, topic: Topic) -> Topic:
    topic.is_pinned = not topic.is_pinned
    db.commit()
    db.refresh(topic)
    return topic
```

`toggle_topic_featured` 与它完全对称（把 `is_pinned` 换成 `is_featured`）。动词是 **`toggle`（切换）而不是 `set`（设值）**，这反映了接口设计的选择：

| 维度 | toggle（本项目） | set |
|------|----------------|-----|
| 前端复杂度 | 低。按钮文案随状态变，点击就发一个请求 | 高。要自己判断该发 `true` 还是 `false` |
| 请求体积 | 无 body | 要带 body |
| **幂等性** | ❌ **非幂等**：调两次等于没调 | ✅ 幂等 |
| 出错恢复 | 状态不一致时再点一次会得到相反结果 | 重试安全 |

**toggle 的最大代价就是"不幂等"**，在网络环境下是真实风险：用户点"置顶"→ 服务端执行成功（`is_pinned` 变 true）→ 响应在网络中丢失 → 前端以为失败报错、用户又点一次 → 服务端又执行成功（变回 false）——用户想要置顶，结果取消了。

项目仍选 toggle，因为权衡了场景：管理员操作频率极低、前端会用响应里的真实状态覆盖本地状态、页面有明确视觉反馈（按钮文字变化）。前端配合的关键在这里：

```javascript
async function handlePin() {
  try {
    const res = await pinTopic(topic.value.id);
    topic.value.is_pinned = res.data.is_pinned;
    showToast.success(res.data.is_pinned ? "已置顶" : "已取消置顶");
  } catch {
    showToast.error("操作失败");
  }
}
```

关键在 `topic.value.is_pinned = res.data.is_pinned`——**本地状态来自服务端响应，而不是自己 `!topic.value.is_pinned` 猜出来的**。请求成功则前端跟着变、一致；请求失败则本地状态**不变**，不会出现"界面上置顶了但服务端没有"的假象。若改成本地取反，风险立刻放大：请求失败时本地还翻转了，界面和服务端就永久不一致。**"状态从服务端响应来，不从本地推测来"——很值钱的一条习惯。**

> `db.refresh(topic)` 在 `commit()` 之后是必要的：`commit` 会让对象属性过期，`refresh` 重新读一遍，保证返回给前端的是数据库里的真实值（含数据库层默认值、`onupdate` 的 `updated_at`）。**只要返回给客户端，就刷新一次。**

### 权限：`require_admin` 与 401/403 的区别

`auth.py` 新增了第三个依赖（前两个是 `get_current_user` / `get_optional_user`）：

```python
def require_admin(
    current_user: User = Depends(get_current_user),
) -> User:
    if not current_user.is_admin:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Admin required")
    return current_user
```

它是一个"依赖链"：**自己不解析 token，把这件事交给 `get_current_user`，只多做一次"是不是管理员"的判断**。于是认证逻辑（token 解析、过期检查、用户查询）只写一遍，`require_admin` 只有 3 行，将来改 token 格式只改 `get_current_user`。**这就是 FastAPI 依赖注入最实用的用法：把"更严格的要求"实现成"依赖更宽松的要求 + 加一个判断"。**

它会返回两种含义完全不同的错误码：

| 状态码 | 含义 | 触发条件 | 用户该怎么办 |
|:------:|------|---------|-----------|
| **401** Unauthorized | "**你是谁？**我不知道" | 未登录、token 无效/过期 | 去登录 |
| **403** Forbidden | "**我知道你是谁**，但你没这个权限" | 已登录但不是管理员 | 登录也没用，就是不给你 |

**为什么必须区分？** 因为前端对这两种码的处理完全不同——项目里的 axios 拦截器（`api/client.js`）遇到 `error.response?.status === 401` 时会清本地 token、跳登录页；**403 则不拦截**，让具体的业务代码去展示"操作失败"提示。**若权限不足时错误地返回 401，就会出现很荒谬的体验：一个已登录的普通用户点了管理员按钮，被踢到登录页，登录回来再点，又被踢走。** 规则：**验证"身份"失败用 401，验证"权限"失败用 403。** 项目里所有权限判断都遵守，包括 `main.py` 里的作者校验 `_author_or_admin`（`topic.author_id != user.id and not user.is_admin` → 403）。

### 两个端点与排序

```python
@app.put("/api/topics/{topic_id}/pin")
def pin_topic_route(topic_id: int, current_user: User = Depends(require_admin), db: Session = Depends(get_db)):
    topic = get_topic_for_edit(db, topic_id)
    if not topic:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Topic not found")
    return toggle_topic_pin(db, topic)
```

`/featured` 端点是同一份代码，只把 `toggle_topic_pin` 换成 `toggle_topic_featured`。四个可以学到的点：**① 用 `PUT`** 表达"更新一个已有资源的某个状态"（严格按 REST，toggle 非幂等其实更适合 `POST`；用 `PUT` 是因为它确实在"改一个资源的状态"，这点语义折中不值得为此改代码）；**② 先查存在性（404）再由依赖判权限（403）**——`Depends(require_admin)` 在请求进入处理函数**之前**执行，所以非管理员访问不存在的帖子会先拿到 403 而不是 404，这正是我们想要的：**不该让没权限的人通过错误码判断出帖子存不存在**；**③ 没有限流装饰器**——只有管理员能调用，而管理员可信，**限流是给"不可信的大多数"准备的**；**④ 没有请求体**——toggle 不需要参数，这正是 toggle 设计带来的接口简洁。

置顶"生效"的地方在列表查询的排序里，`crud.get_topics` 的取数查询用的是 `query.order_by(Topic.is_pinned.desc(), Topic.created_at.desc())`（即 `ORDER BY is_pinned DESC, created_at DESC`）。

两级排序：`is_pinned DESC` 让 `True`(=1) 排在 `False`(=0) 前面，**置顶帖永远在普通帖之前**；`created_at DESC` 让同级内部按时间倒序（新的在前）。`DESC` 用在布尔列上是 PostgreSQL 里排序布尔值的标准写法。**注意置顶帖之间仍按时间排，不是按"哪个先被置顶"**——表里没存"置顶时间"，这是简化带来的小限制（若要"最后置顶的排最前"，得再加 `pinned_at`）。

> `get_topics_by_user`（个人主页）**没有**用这个排序，用的是纯 `created_at.desc()`。去某人主页看他的帖子，看的是"他发了什么"，置顶是首页的编辑行为，不该污染个人主页的时间线。**同一张表，不同场景用不同排序，是正常且必要的。** 同理，响应模型 `TopicListResponse` / `TopicDetailResponse` 里都给这两个字段写了默认值 `is_pinned: bool = False`——**给老客户端兜底**，接口没返回时 Pydantic 用 `False` 补上，前端 `v-if="t.is_pinned"` 不会因 `undefined` 报错。**响应模型给新字段加默认值，是"加字段不破坏兼容"的标准做法。**

前端只有管理员看得见按钮（`TopicDetailView.vue`）：

```html
<div v-if="isAuthor || isAdmin" class="author-actions">
  <template v-if="isAdmin">
    <button class="btn-action btn-pin" :class="{ active: topic.is_pinned }" @click="handlePin">
      {{ topic.is_pinned ? '取消置顶' : '置顶' }}
    </button>
    <button class="btn-action btn-feature" :class="{ active: topic.is_featured }" @click="handleFeature">
      {{ topic.is_featured ? '取消精华' : '精华' }}
    </button>
  </template>
</div>
```

`isAdmin = computed(() => auth.user?.is_admin)`（可选链兜底用户信息未加载）。两层 `v-if` 区分得很清楚：外层"作者或管理员"（编辑、删除按钮），内层"仅管理员"（置顶、精华按钮）。**toggle 接口的另一半好处在这里体现**：按钮文案随 `topic.is_pinned` 变（配合 `:class="{ active: ... }"` 高亮），前端不需要传值，只需正确地"显示当前状态"和"显示下一步操作"。徽章（`.badges` 里的 `.badge.pin` / `.badge.featured`）则所有访客可见、含未登录，因为徽章只是信息展示：置顶用主色，精华用 `--color-warning`（`#b8860b`，深金/琥珀），不用读文字也能分辨。

## 2. 头像上传：从"能用"到"安全"

`avatar` 字段本来就能填图片 URL（`ProfileEdit.vue` 里保留着"或输入图片 URL"入口），为什么还要做上传？因为**绝大多数用户没有图床**——让人去注册图床拿外链再贴回来，是把产品的技术细节强加给用户。相关提交：

### 配置、目录与配套

```python
# ── Upload config ──

UPLOAD_DIR = "uploads"
AVATAR_DIR = os.path.join(UPLOAD_DIR, "avatars")
MAX_AVATAR_SIZE = 2 * 1024 * 1024  # 2MB
ALLOWED_IMAGE_TYPES = {"image/jpeg", "image/png", "image/gif", "image/webp"}
```

把四个常量提到模块顶部而不是写在函数里，好处是规则集中可见（想知道"头像最大多大"不用在读业务逻辑时找）。`MAX_AVATAR_SIZE = 2 * 1024 * 1024` 写成算式而不是 `2097152`，一眼能看出是 2MB。目录创建放在 `lifespan`：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    os.makedirs(AVATAR_DIR, exist_ok=True)
    ensure_schema()
    yield
```

`exist_ok=True` 又是幂等思想——目录已存在也不报错。配套动作还有两个：`docker-compose.yml` 给后端挂了卷 `./backend/uploads:/app/uploads`（**没有它，容器一重启上传的图片就全没了**，容器内文件系统不持久），`.gitignore` 忽略 `backend/uploads/`（**用户上传的内容不该进代码仓库**）。这两件事很容易在开发时被忘掉，等到上线后用户头像批量消失才发现。

### 上传端点：四层校验

```python
@app.post("/api/upload/avatar")
@limiter.limit("10/minute")
async def upload_avatar(
    request: Request,
    file: UploadFile = File(...),
    current_user: User = Depends(get_current_user),
):
    if file.content_type not in ALLOWED_IMAGE_TYPES:
        raise HTTPException(status_code=400, detail="不支持的文件类型，请上传 JPG/PNG/GIF/WebP 图片")

    content = await file.read()
    if len(content) > MAX_AVATAR_SIZE:
        raise HTTPException(status_code=400, detail="文件大小不能超过 2MB")

    # 验证文件魔术字节，防止伪造 content-type
    detected = _detect_image_type(content)
    if detected not in ("jpeg", "png", "gif", "webp"):
        raise HTTPException(status_code=400, detail="文件内容不是有效图片")

    # 扩展名由检测出的真实格式决定，不信任用户文件名
    filename = f"{uuid.uuid4()}{EXT_BY_TYPE[detected]}"
    filepath = os.path.join(AVATAR_DIR, filename)

    with open(filepath, "wb") as f:
        f.write(content)

    return {"url": f"/uploads/avatars/{filename}"}
```

第三层的 `_detect_image_type()` 是 `main.py` 里的一个模块级小函数，手写比对四种格式的文件头：

```python
def _detect_image_type(content: bytes) -> str | None:
    """按魔术字节识别图片类型（替代 Python 3.13 已移除的 imghdr）。"""
    if content.startswith(b"\xff\xd8\xff"):
        return "jpeg"
    if content.startswith(b"\x89PNG\r\n\x1a\n"):
        return "png"
    if content.startswith((b"GIF87a", b"GIF89a")):
        return "gif"
    if len(content) >= 12 and content[:4] == b"RIFF" and content[8:12] == b"WEBP":
        return "webp"
    return None
```

十几行、零依赖。注意 WebP 的判断比另外三种麻烦：它的文件头不是从第 0 字节开始的固定串，而是 `RIFF`（0–3 字节）+ 4 字节长度 + `WEBP`（8–11 字节），所以要跳过中间的长度字段——**这也是手写魔术字节最容易漏掉的一处**。

**这段代码原来是坏的，第 4 节专门讲。** 现在按"设计意图"看它的四层校验：① content-type 白名单（声明）→ ② 读字节 + 大小 ≤ 2MB（体积）→ ③ 魔术字节校验（内容）→ ④ uuid4 重命名 + 落盘（文件名由我们决定）。这套分层思路本身非常值得学。

**① content-type 白名单——防"明显的手误"，不能防攻击者。** `content_type` 来自请求头，是**客户端自己声明的**：浏览器上传时会按扩展名自动填，但攻击者用 `curl` 可以随便填成 `image/png`。它的价值不在安全，而在对普通用户的友好报错（选了 PDF 会得到提示）和挡掉绝大多数手误。**看到"只校验 content-type"的代码，就要知道它等于没做安全校验。**

**② `len(content)` 大小校验——防资源耗尽（DoS）。** 没有它，任何人都能上传一个 10GB 的文件把磁盘写满。要注意**顺序问题**：这里是先 `read()` 再判断大小，意味着那 10GB 已经被读进内存了才被拒——服务器可能在判断之前就 OOM。更严谨的做法是**分块读、超限立刻中断**（`while chunk := await file.read(64 * 1024)` 累加并判断），因为 `UploadFile` 底层的 `SpooledTemporaryFile` 小文件放内存、大文件落磁盘，`file.read()` 会把全部内容一次性读出来。对 2MB 上限的头像问题不大，但将来放开到 20MB 就该改。

**③ 魔术字节校验——这才是真正的安全层。** "魔术字节"是文件开头几个字节，每种格式有固定特征值：JPEG `FF D8 FF`、PNG `89 50 4E 47 0D 0A 1A 0A`、GIF `47 49 46 38`、WebP `52 49 46 46 ... 57 45 42 50`。为什么必须校验？因为 content-type 是客户端说的，而魔术字节由文件**真实内容**决定。攻击者可以上传一个内容为 HTML、请求头写 `image/png` 的文件，落盘后把 URL 发给别人，别人的浏览器打开就按 `text/html` 执行里面的 `<script>`——**存储型 XSS**。第③层把这条路堵死：**内容不是图片就 400，随便你请求头怎么说。**

**④ `uuid.uuid4()` 重命名——让文件名由服务器决定。** `file.filename` 是用户提供的**完全不可信**的字符串，直接拿它当文件名有三个问题：路径穿越（`../../../etc/passwd` 可覆盖任意文件）、覆盖已有文件（`alice.jpg` 把别人的头像覆盖掉）、特殊字符（`a?b*c:d.jpg` 在 Windows 上写入失败）。用 `uuid4()` 生成随机名（32 位十六进制，不可预测、不会重复、无特殊字符），三个问题一次解决。**"用户提供的名字只用来参考，落盘名字由服务器生成"——所有文件上传功能的铁律。**

> `UploadFile` 依赖 **`python-multipart`** 这个包，`requirements.txt` 里列了它。**漏掉的话 FastAPI 会在启动时直接报错**（不是运行时）：它在注册路由时就要检查 multipart 解析器是否可用，报 `RuntimeError: Form data requires "python-multipart" to be installed.`——这是个"依赖写漏了立刻就知道"的少见例子（大多数缺依赖的错误要等那条代码真的被执行才暴露）。**看到 `File(...)`/`Form(...)`，就要想到 `python-multipart`。**

### 静态托管与"9 分钟"的代理修复

文件写到 `uploads/avatars/` 了，但 `/uploads/avatars/xxx.jpg` 这个 URL 要能访问到它，一行搞定：

```python
# ── Static files ──

app.mount("/uploads", StaticFiles(directory=UPLOAD_DIR), name="uploads")
```

`app.mount()` 把一个**子应用**挂到某个路径前缀上；`StaticFiles(directory="uploads")` 是现成的 ASGI 应用，负责把 URL 映射成磁盘文件：`/uploads/avatars/xxx.jpg` → 去掉前缀 `/uploads` → 剩下的路径拼到 `directory` 上 → 读文件、按扩展名推断 Content-Type 返回。

**为什么上传接口返回的是相对路径？** 注意返回的是 `/uploads/avatars/xxx.jpg` 而不是 `http://localhost:8000/...`。返回带 host 的绝对 URL 会**把部署地址写死进数据库**（开发时存 `localhost:8000`，上线后所有头像链接全指向 localhost，改都改不过来）；返回相对路径，浏览器会自动用它当前的域名去请求，**开发走 vite 代理、生产走 nginx 代理，同一份数据在哪都能用**。

现在回到那两条相隔 9 分钟的提交。上传功能做完后图片显示不出来，原因是**"同源"**：`/uploads/...` 是相对路径，浏览器会向**当前页面所在的域名**（5173，vite）请求，而文件其实在 8000（FastAPI）上——vite 那里没有 `/uploads` 这个路径，直接 404。修法就是在 vite 配置里加一条代理（与既有的 `/api` 代理并列）：

```javascript
export default defineConfig({
  plugins: [vue()],
  server: { proxy: {
    "/api": { target: "http://localhost:8000", changeOrigin: true },
    "/uploads": { target: "http://localhost:8000", changeOrigin: true },
  } },
})
```

生产环境的 nginx 也配了对应的转发（`frontend/nginx.conf`）：

```nginx
    # Uploads proxy to backend
    location /uploads/ {
        proxy_pass http://backend:8000;
        proxy_set_header Host $host;
    }
```

**这里有个非常值得记住的规律：`/api` 和 `/uploads` 是两条"需要代理到后端"的路径。** 加一条新的后端路径前缀时，必须**同时**在开发（vite）和生产（nginx）两处都加上代理，否则就会出现"本地正常、上线挂掉"或者反过来。**两套环境，同一个规则**，这样前端代码里写 `/uploads/xxx` 就能在两种环境下都工作。

> 这也解释了为什么第③层校验（魔术字节）那么重要：`/uploads` 目录被**原样对外暴露**，任何落盘的文件都能通过 URL 访问——它不只是"存起来"，它是"发布出去"。

## 3. 前端 `ProfileEdit.vue`：blob 预览与保存

```javascript
function handleFileSelect(e) {
  const file = e.target.files[0];
  if (!file) return;
  avatarFile.value = file;
  // 释放上一次的 ObjectURL 避免内存泄漏
  if (avatarPreview.value && avatarPreview.value.startsWith("blob:")) {
    URL.revokeObjectURL(avatarPreview.value);
  }
  avatarPreview.value = URL.createObjectURL(file);
}
```

核心是 `URL.createObjectURL(file)`——**它能在不发任何网络请求的情况下，给本地文件生成一个可访问的临时 URL**，于是选完图立刻就出现在头像框里。对比"上传完再预览"：后者要看网络脸色，图片大或网络慢时有几百毫秒到几秒的空档。**"用户选了文件 → 立刻看到结果"是文件上传体验里最重要的一环。**

`URL.createObjectURL` 创建的 blob URL **不会被垃圾回收自动释放**——只要那个 URL 字符串还存在，浏览器就一直把文件内容留在内存里（用户连选 5 张 5MB 的图，不释放就白占 25MB）。所以规则是**创建新 blob URL 之前先释放旧的**。三个细节：① `startsWith("blob:")` 判断是必须的，因为 `avatarPreview` 的初始值是用户的**已有头像 URL**（`https://...` 或 `/uploads/...`），那种**不能** revoke；② 只 revoke 上一次的、不要 revoke 当前这个，否则预览图立刻变裂图；③ 严格说组件卸载时也该 revoke 一次，但这里最多只留一个 blob URL、风险很低，可以接受。

**保存是"先上传，再保存"的两步操作：**

```javascript
async function handleSave() {
  error.value = "";
  success.value = false;
  saving.value = true;
  try {
    let avatarUrl = avatar.value;

    // 如果选择了新文件，先上传
    if (avatarFile.value) {
      uploading.value = true;
      const res = await uploadAvatar(avatarFile.value);
      avatarUrl = res.data.url;
      uploading.value = false;
    }

    const res = await updateMe({
      avatar: avatarUrl || null,
      bio: bio.value || null,
      github_url: githubUrl.value || null,
    });
    auth.user = res.data;
    localStorage.setItem("user", JSON.stringify(res.data));
    success.value = true;
  } catch (e) {
    uploading.value = false;
    error.value = e.response?.data?.detail || "保存失败";
  } finally {
    saving.value = false;
  }
}
```

**为什么分成上传和更新两个接口，而不是一个 `PUT /api/auth/me` 直接带文件？** 因为语义不同：上传文件是"创建了一个资源、返回它的地址"，更新资料是"修改用户记录"。混在一起会让 `/api/auth/me` 同时处理 JSON 和 multipart 两种请求体，复杂度陡增；分开后上传接口还能被复用（将来帖子封面图也是上传到别的目录），资料接口保持纯粹。

`avatar: avatarUrl || null` 里的 `|| null` 把空字符串转成 `null`——回头看 `crud.update_user` 的条件是 `if data.get(field) is not None`，**`null` 表示"不改这个字段"**。传 `""` 会把字段设成空字符串，传 `null` 则跳过。这个语义有个副作用：**用户永远无法清空自己的简介**（填了想删掉，前端传的是 `bio.value || null`，为空时传 `null` 于是"清不掉"）。这是"部分更新语义"与"可选字段可清空"之间的固有张力，要彻底解决需引入第三个状态（如 `PATCH` + JSON Merge Patch）。**当前规模不值得为它增加复杂度，但要知道它存在。**

`uploading` 和 `saving` 两个状态分成两层，是为了给用户更准确的反馈（上传慢时显示"上传中…"而不是笼统的"保存中…"）。注意 `catch` 里也要 `uploading.value = false`：**上传失败时这个标志会卡在 `true`，一次失败之后界面就永远显示"上传中"**——所有异步状态标志都必须在 `catch` 或 `finally` 里重置（这里其实可以改进：`uploading.value = false` 该放 `finally` 而不是两处各写一遍）。最后 `auth.user = res.data` + `localStorage.setItem(...)` 要**同时更新内存状态和 localStorage**：更新 store 让当前页面立刻刷新头像，更新 localStorage 让刷新浏览器后仍是新头像，漏掉任何一半都有问题。

上传 API 层用 `FormData`：`const formData = new FormData(); formData.append("file", file);` 然后 `client.post("/upload/avatar", formData)`。两点要注意：**`append` 的字段名必须和后端 `File(...)` 的参数名对上**（后端是 `file`，对不上 FastAPI 会返回 422 说缺少必填字段，这是上传功能最常见的低级错误）；**手动设置 `Content-Type: multipart/form-data` 其实有个坑**——它必须带 `boundary`（分隔各部分内容的分隔符），而 boundary 是浏览器根据内容生成的，手写反而可能把它覆盖掉。**更稳的写法是干脆不写这个 header**，让 axios 识别 `FormData` 后自己补上带 boundary 的正确 Content-Type；当前代码显式写了它，能工作但多一行、还隐含了那个风险点。

## 4. 一个真实的 bug：`imghdr.from_buffer` 不存在

**这个端点曾经是坏的**（2026-09-26 修复，改法见下面的方案四）。它坏掉时的现象是：调用 `POST /api/upload/avatar`，无论上传多正确的图片都得到 `500 Internal Server Error`；日志里（因为 `main.py` 配了完整 traceback 记录）是：

```
ERROR 500 on POST /api/upload/avatar: module 'imghdr' has no attribute 'from_buffer'
AttributeError: module 'imghdr' has no attribute 'from_buffer'
```

问题就在 `imghdr.from_buffer` 这个名字上。**`imghdr` 模块从来就没有 `from_buffer` 这个函数。** 它的完整公开 API 只有两个：`imghdr.what(file, h=None)`（判断图片类型，返回 `'jpeg'`/`'png'`/`'gif'`/`'webp'`/`None`）和 `imghdr.tests`（内部用的检测函数列表）。

`what(file, h=None)` 的用法是：**要么传一个文件路径（`file`），要么传 `h`（已经读出来的字节）**。所以"检测一段 bytes"的正确写法是 `imghdr.what(None, content)`。`from_buffer` 这个名字大概率是**凭直觉推出来的**——"从 buffer 里检测"，听着很合理，但标准库里没有这个 API。**这类 bug 的教训不是"要背 API"，而是"写完要真的跑一次"。**

注意 `import imghdr` 写在了**处理函数内部**：应用启动时只是加载 `main.py`、定义 `upload_avatar` 函数，函数体不执行，所以 `import imghdr` 那一行根本没跑过——**启动成功、健康检查多少次都不会暴露问题**；直到用户第一次上传头像，执行到 `imghdr.from_buffer` 才 `AttributeError 💥 500`。

**在函数内部 import 的代价就在这儿**：它把"模块是否可用"的检查从启动时推迟到了调用时。用它做延迟导入（可选依赖、避免循环导入）是可以的，但要意识到这个后果——**启动时能发现的错误，才是最好的错误。** 这里 `imghdr` 是标准库、不存在循环导入问题，写成函数内 import 看不出必要，**反而刚好把 bug 藏了起来**。

**更麻烦的背景：`imghdr` 本身正在消失。** 即使把 `from_buffer` 改成正确的 `what`，问题也没真正解决，因为 **`imghdr` 已被官方废弃（PEP 594）**：

| Python 版本 | `imghdr` 的状态 |
|------------|----------------|
| ≤ 3.10 | 正常可用 |
| **3.11** | **标记为 deprecated**（PEP 594），导入时有 `DeprecationWarning` |
| 3.12 | 仍存在，但已明确"将在 3.13 移除" |
| **3.13** | **已从标准库中移除**，`import imghdr` 直接 `ModuleNotFoundError` |

而项目的 `backend/Dockerfile` 用的是 `FROM python:3.12-slim`，**3.12 这里还活着所以能 import 成功，但升级到 3.13 之后连 `import imghdr` 这一步都会失败**。两条路都通向 500，只是错误信息不同（`AttributeError` → `ModuleNotFoundError`）。**所以"改成 `imghdr.what`"只是治标，真正该做的是换掉这个库。**

### 四种修法

**方案一：最小改动（治标，适用于"现在就要能跑"）。** 只把函数名改对：

```python
    # 验证文件魔术字节，防止伪造 content-type
    import imghdr
    detected = imghdr.what(None, content)      # ← 第一个参数传 None，第二个传字节
    if detected not in ("jpeg", "png", "gif", "webp"):
        raise HTTPException(status_code=400, detail="文件内容不是有效图片")
```

改完在 Python ≤ 3.12 上立刻能工作。`what()` 返回的基名 `"jpeg"`/`"png"`/`"gif"`/`"webp"` 和原来的判断完全一致，所以 `if` 那行不用动——**这也是为什么原来的代码"看起来是对的"：判断逻辑确实对，只有函数名错了。**

**方案二：换 Pillow（检测强度最高）。** Pillow 不仅检测格式，还能验证"这真的是一个能打开的图片"，而不只是"文件头长得像图片"：

```python
from io import BytesIO

from PIL import Image, UnidentifiedImageError

IMG_FORMATS = {"JPEG", "PNG", "GIF", "WEBP"}
EXT_BY_FORMAT = {"JPEG": ".jpg", "PNG": ".png", "GIF": ".gif", "WEBP": ".webp"}


def _detect_image_format(content: bytes) -> str | None:
    """用 Pillow 检测真实图片格式，非法图片返回 None"""
    try:
        with Image.open(BytesIO(content)) as img:
            img.verify()            # 真正解析文件结构，损坏/伪造的文件会在这里抛异常
            return img.format       # "JPEG" / "PNG" / "GIF" / "WEBP"
    except (UnidentifiedImageError, OSError):
        return None
```

比方案一多修了两件事，**这两点比"把函数名改对"更重要**：

**① `img.verify()` 从"看起来像"升级到"真的是"**：`imghdr.what()` 只看文件开头几个字节，一个"前 3 字节是 `FF D8 FF`、后面全是垃圾"的文件也能通过；`img.verify()` 会真正解析文件结构，**损坏的、刻意构造的畸形文件都会被拒**（它不解码整张图、不解码像素，所以开销依然很小）。

**② 扩展名由检测出的真实格式决定，不再来自 `file.filename`。** 原来虽然用 uuid 挡住了路径穿越，但**扩展名仍然由攻击者控制**——攻击者可以构造"内容是真的 PNG、文件名是 `avatar.html`"的文件，访问时 `StaticFiles` 按扩展名返回 `Content-Type: text/html`。内容虽是图片、浏览器不会执行 HTML，但**响应头是 `text/html` 本身就是个不该有的状态**，它给了内容嗅探、以及将来把校验改松之后形成 XSS 的可能性。修法很简单：既然已经知道真实格式了，为什么还要问用户？于是把 `ext = os.path.splitext(file.filename)[1] ...` 那行换成 `filename = f"{uuid.uuid4()}{EXT_BY_FORMAT[fmt]}"`。

Pillow 需要加进 `requirements.txt`（`Pillow>=10.0`）。代价是引入了一个非纯 Python 的依赖（会编译 C 扩展），镜像体积会增加几 MB——**对"要么安全、要么不装"的取舍来说，这个代价值得。**

**方案三：用 `filetype`（纯 Python，轻量）。** 不想引入 Pillow 的话：`kind = filetype.guess(content)`，`kind` 为 `None` 或 `kind.mime` 不在白名单里就 400；落盘时用 `filename = f"{uuid.uuid4()}.{kind.extension}"`。

| 方案 | 依赖 | 检测强度 | 适用 |
|------|------|---------|------|
| `imghdr.what(None, content)` | 标准库（即将消失） | 弱：只看文件头 | 临时修复 |
| **Pillow** | `Pillow`（C 扩展） | **强：`verify()` 真正解析结构** | 安全要求高时 |
| `filetype` | `filetype`（纯 Python） | 中：也是看文件头，但库维护活跃 | 想避免 C 依赖时 |

**方案四：手写魔术字节比对（本项目实际采用）。** 前面三个方案都要引入一个库（连标准库 `imghdr` 也是库，而且正在消失），但这里要识别的只有四种格式、每种的特征值都是固定的几个字节，**手写十几行反而比引依赖更划算**——这就是第 2 节贴的 `_detect_image_type()`。它把检测逻辑收进一个模块级函数，顺带修掉了旧代码的另一个毛病：`import imghdr` 原来写在**请求处理函数内部**，改到模块级后，任何导入错误都会在启动时就暴露，而不是等到用户第一次上传头像。

前三个方案**都顺带解决了"扩展名该从哪来"的问题**，而方案四最初**没有**——它只返回类型名，落盘用的仍是 `ext = os.path.splitext(file.filename)[1]`，扩展名依旧来自用户文件名。也就是说，方案二里说的"攻击者可以构造内容是真 PNG、文件名是 `avatar.html` 的文件，让 `StaticFiles` 返回 `Content-Type: text/html`"这个隐患在方案四落地后**依然存在了一天**。好在修法只有一行，当天就补上了（`EXT_BY_TYPE` 定义在 `main.py` 的上传配置处）：

```python
EXT_BY_TYPE = {"jpeg": ".jpg", "png": ".png", "gif": ".gif", "webp": ".webp"}
filename = f"{uuid.uuid4()}{EXT_BY_TYPE[detected]}"   # 扩展名由检测结果决定，不再问用户
```

**现在的代码已经是修好的版本**：第 2 节贴的端点代码里，落盘那一行就是 `EXT_BY_TYPE[detected]`。

**这个案例真正的价值：** 记住 `from_buffer` 改成 `what` 没什么意义，值得记住的是它暴露出来的几件事：

1. **"看起来对"的代码最危险。** 这段代码的注释（"验证文件魔术字节，防止伪造 content-type"）完全正确，`if detected not in (...)` 的判断也完全正确，只有中间那个函数名是错的——**审核代码时很容易被正确的意图和正确的判断骗过去**，唯一的检验方式是执行一遍。
2. **校验逻辑必须有测试覆盖。** 如果有一个"上传一张 PNG，期望 200、期望返回 `url` 字段"的测试，第一次跑就会红。**"安全意识"不能只体现在注释上，要体现在能跑起来的测试用例上。**
3. **多层校验的价值在"分层"，不在"层数"。** 这个 bug 让第③层完全失效，但**另外两层仍然有效**（content-type 白名单挡住了明显的手误，大小限制挡住了资源耗尽）。**这就是分层的意义：任何一层的失效不会让整体归零。**
4. **"修好了报错"不等于"修好了问题"。** 方案四让端点从必然 500 变成正常工作，但它没有回答方案二提出的"扩展名该信谁"——**同一个函数里两个独立的问题被一个 bug 盖住了**，修掉显眼的那个之后，安静的那个才露出来。修 bug 时不妨问一句：这段代码除了坏掉的地方，还有没有"因为坏掉所以没暴露"的问题？

## 本章要点

- 置顶/加精用 `Topic.is_pinned` 和 `Topic.is_featured` **两个布尔字段**，不建独立表——因为"候选值少 + 每帖最多一个值 + 查询频繁"三者都指向主表列（对比第十八章 `topic_tags` 三条全不满足，所以必须是独立表）
- 加字段要配迁移：`ensure_schema()` 用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 做轻量迁移，**`IF NOT EXISTS` 保证可反复执行**（启动时每次都会跑）
- `toggle_topic_pin` / `toggle_topic_featured` 是**切换**语义而非设值：前端不需要知道当前状态，但**非幂等**，重复调用会来回翻转
- 前端必须用 `topic.is_pinned = res.data.is_pinned`（**状态从服务端响应来**），绝不能本地 `!topic.is_pinned` 推测，否则请求失败会造成界面与服务端永久不一致
- `require_admin` 复用 `get_current_user`，只有 3 行——**把"更严格的要求"实现成"依赖更宽松 + 加一个判断"**
- **401 = 你没登录，403 = 你登录了但没权限**，必须严格区分：前端拦截器只对 401 跳登录页，权限不足返回 401 会导致"已登录用户被反复踢到登录页"的荒谬体验
- 列表排序 `order_by(Topic.is_pinned.desc(), Topic.created_at.desc())`，置顶是第一优先级；但 `get_topics_by_user`（个人主页）**不用**这个排序，保持纯时间线
- 上传端点的四层校验各防不同威胁：**①content-type 白名单**（只挡手误，客户端可伪造）→ **②大小限制**（挡资源耗尽）→ **③魔术字节**（真正的安全层，防伪造 content-type）→ **④uuid4 重命名**（防路径穿越与覆盖）
- `uuid.uuid4()` 重命名让落盘文件名由服务器决定，**用户提供的文件名完全不可信**
- 上传返回**相对路径** `/uploads/avatars/x.jpg`，不写死域名；`app.mount("/uploads", StaticFiles(...))` 提供静态托管
- **`/uploads` 必须同时配 vite（开发）和 nginx（生产）代理**，`0075575` 就是补 vite 这一条——这个修复与上传功能只隔了 9 分钟
- `UploadFile` 依赖 **`python-multipart`**，漏了会在**启动时**报 `RuntimeError: Form data requires "python-multipart" to be installed`
- ✅ **`imghdr.from_buffer` 不存在**（`imghdr` 只有 `what(file, h=None)`），这个函数名错了曾让端点必然 `AttributeError` → 500；又因为 `import imghdr` 写在函数内部，启动时不暴露。**2026-09-26 已改为模块级 `_detect_image_type()` 手动比对魔术字节**（顺带把检测提到模块级，导入错误现在启动即暴露）
- ✅ **`imghdr` 自 Python 3.11 废弃、3.13 已移除**（`Dockerfile` 用 `python:3.12-slim` 所以当时还能 import）——所以"改成 `what()`"只是治标，本项目选择直接不再依赖它，也没有引入 Pillow / filetype
- ✅ **落盘扩展名也不再信用户文件名**：原来用 `ext = os.path.splitext(file.filename)[1]`，"真实图片内容 + `.html` 扩展名 → 静态托管返回 `text/html`"这条路径在 2026-09-26 当天被跟进修掉：`filename = f"{uuid.uuid4()}{EXT_BY_TYPE[detected]}"`。教训是"修好了报错"不等于"修好了问题"——同一个函数里被 500 盖住的第二个问题，要在修完第一个之后回头再看一眼
- 前端用 `URL.createObjectURL(file)` 做**零延迟本地预览**（不等上传完成），创建新 URL 前先 `revokeObjectURL` 释放旧的防内存泄漏（只 revoke `blob:` 开头的）
- 保存是两步：先 `uploadAvatar` 拿 `res.data.url`，再 `updateMe({ avatar: url })`；成功后要同时更新 `auth.user`（当前页面）和 `localStorage`（刷新后）
- **这个 bug 最值钱的教训**：注释对、判断对、只有函数名错——"看起来对"的代码最难靠阅读发现，**唯一可靠的检验是真跑一遍，所以校验逻辑必须有测试覆盖**
